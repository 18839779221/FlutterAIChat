# 架构文档编写规范

本目录下的文档用于描述项目的稳定架构、边界和约束，不用于记录需求演进、改造过程或阶段性任务清单。

## 写作原则

- 只写当前成立的架构事实与长期约束
- 只写“系统应如何工作”，不写“这次是怎么改出来的”
- 只写边界、职责、语义、约束、验证要求
- 不写产品需求叙事、历史回顾或实现流水账

## 推荐结构

优先使用以下结构，按需裁剪：

1. `目标`
2. `核心定义`
3. `总体架构`
4. `模块边界`
5. `数据或路径模型`
6. `约束与禁止事项`
7. `验证要求`
8. `相关文档`

## 术语要求

- 术语要稳定、可复用、前后一致
- 对外可见的路径、状态、对象名必须与代码语义对齐
- 如果存在 agent 视角与 host 视角，必须明确区分
- 如果存在 UI、ledger、transcript、runtime 等分层，必须明确职责边界

## 约束写法

- 使用“必须 / 不得 / 仅允许 / 只应”等约束性表述
- 不要写模糊建议句
- 不要把实现细节伪装成协议
- 不要把历史迁移步骤混入架构正文

## 反模式

- 不写“原来怎样、现在怎样”的改造叙述
- 不写任务拆解、执行计划或里程碑
- 不写兼容方案，除非它本身就是架构约束
- 不写临时 workaround

## 文件要求

- 文档应短而稳定，避免过度展开
- 新增专题文档时，优先链接到已有架构文档
- 若新增约束会影响多个模块，应把它写成独立架构文档，并在 `docs/architecture/project-architecture-overview.md` 中挂入口

## 维护要求

- 当架构约束变化时，必须同步更新相关专题文档
- 当新增专题文档时，必须检查是否需要更新总览页和 README
- 若文档内容和实现不一致，以当前实现与当前约束为准，及时修正文档
