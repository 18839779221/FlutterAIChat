# Tool 展示边界与可插拔渲染约束

## 目标

本文档定义 Tool 执行产物与 UI 展示层之间的推荐边界，约束后续 tool workflow、tool result、专属卡片、时间线投影与富媒体展示相关迭代，避免展示语义持续回流到执行主链。

本文档重点关注两件事：

1. 框架边界应该如何划分
2. 展示能力如何保持可插拔

本文档不讨论某个具体工具该如何设计 UI，也不把任何单一工具当作架构中心。

## 一句话边界

上游负责产出阶段性事实。
下游负责消费事实并决定展示。

这里的“上游”指 Tool Call、Turn Ledger 及其相关结构化执行产物。
这里的“下游”指默认 renderer、专属 renderer、时间线 block builder 以及其它面向 UI 的投影消费者。

换句话说：

- 上游不强制每个阶段必须对应一个 UI 实体
- 下游不改写执行语义，只在既有事实之上做消费与组合

## 为什么要这样划分

如果执行层直接预设 UI 结构，长期会出现三个问题：

1. 执行事实与展示实体被绑死
   某个阶段存在于 ledger，并不意味着用户一定需要看见一个同名卡片。

2. 新展示类型只能靠主链特判接入
   一旦某类工具需要更特殊的视觉交付形态，就会逐步侵入 block builder、timeline merge、tool orchestration 等不该理解展示语义的层。

3. 刷新与更新语义难以统一
   “刷新某张卡片”不是稳定边界；更稳定的问题应是“输入事实变化后，展示投影如何重算”。

因此，框架边界应固定为：

- 上游稳定产出结构化阶段事实
- 中间层提供统一的展示消费输入
- 下游 renderer 自主决定消费哪些事实、如何组合这些事实、以及最终是否展示

## 分层模型

建议把 Tool 展示相关链路固定理解为以下三层：

```mermaid
flowchart LR
    A["Tool Call / Turn Ledger"] --> B["Presentation Event Feed"]
    B --> C["Default / Specialized Renderers"]
```

### 1. Tool Call / Turn Ledger

这一层负责产出稳定事实，不负责决定 UI 是否渲染。

它应稳定表达的内容包括：

- 工具标识
- 阶段或状态
- turn / step / invocation 标识
- 时间信息
- 结构化参数
- 结构化结果
- 执行策略与权限快照

它不应承担：

- 某个阶段是否需要展示
- 某种展示是否应该弱化或跳过
- 某类内容是否应该以卡片、内联行、富媒体预览或其它形态出现
- 某些事件是否应被聚合后再显示

### 2. Presentation Event Feed

这一层负责把上游事实整理成 UI 可稳定消费的标准化输入。

它的职责是：

- 标准化展示层输入
- 尽量减少具体 renderer 对原始消息编码的依赖
- 让默认 renderer 与专属 renderer 消费同一套事实模型

它不负责决定最终视觉形态。

它应该回答的问题包括：

- 当前有哪些可消费的阶段事件
- 哪些事件属于同一个执行单元
- 哪些事件属于同一个逻辑资源
- 当前时刻有哪些结构化事实可供展示层选择

它不应回答的问题包括：

- 必须渲染哪种卡片
- 哪个阶段是否必须可见
- 某类工具是否应该只展示最终交付物

### 3. Default / Specialized Renderers

这一层负责真正的展示消费策略。

它可以自主决定：

- 消费全部阶段
- 只消费部分阶段
- 聚合同一执行单元的多个事件后展示
- 聚合同一逻辑资源跨阶段或跨 turn 的事件后展示
- 跳过某些事件，不做任何可见 UI

这里的 `default renderer` 只是通用兜底消费器。
这里的 `specialized renderer` 是与之并列的专属消费器，而不是主链例外。

## 核心约束

### 约束 1：上游只生产事实，不预设 UI 实体

上游模型的职责是表达执行语义，而不是直接等价于某一张 UI 卡片。

因此：

- 某个阶段可以存在于 ledger，但 UI 可以不展示它
- 相同事实可以由不同 renderer 以不同方式表现
- 某类事实可以成为通用卡片输入，也可以只成为专属视图输入

### 约束 2：默认卡片只是默认消费器

workflow card、result card、compact row、confirmation row 等现有通用展示，都应被视为默认消费方式，而不是唯一合法展示实体。

这意味着：

- 某些工具类型可以不展示 workflow 类卡片
- 某些工具类型可以不展示 result 类卡片
- 某些工具类型可以只展示最终交付物
- 某些工具类型可以把多个阶段折叠为一个统一表面

### 约束 3：专属展示通过消费策略接入，而不是主链散落特判

未来如果某类工具需要专属展示，应优先通过以下方式实现：

1. 上游继续产出标准化阶段事实
2. 中间层把事实整理成统一 feed
3. 专属 renderer 选择性消费这些事实并产出自定义展示

不推荐的方式：

- 在执行主链中扩散 UI 语义
- 在 timeline merge 中持续增加工具名分支
- 让每个专属 widget 自己扫描整段消息历史反推状态

### 约束 4：刷新首先是投影重算，其次才是 Widget 重建

后续如果要支持统一刷新能力，推荐先把问题定义为：

- 当输入事实集合变化时，展示投影如何重算

而不是：

- 某个组件如何持有私有刷新协议

原因是：

- Widget 生命周期本来就由 Flutter 管理
- 真正需要统一的是“输入事实”与“展示投影”之间的边界
- 逻辑资源的后续更新、旧展示失效、新展示成为当前态等语义，本质上属于投影重算问题

## 可插拔思想

可插拔不只是“能注册一个 Widget”。
更完整的可插拔应该体现在三个层面：

### 1. 输入可插拔

不同 renderer 应消费同一套标准化输入，而不是各自重新解释底层消息结构。

这样可以保证：

- 新 renderer 接入成本可控
- 老 renderer 不因消息编码微调而大量破裂
- 框架能逐步把 UI 从原始消息扫描迁移到稳定 projection

### 2. 消费策略可插拔

renderer 的可插拔重点不是“样式不同”，而是“消费策略不同”。

同一套输入下，renderer 可以属于不同类别：

- 全阶段消费型：消费大部分或全部阶段，适合需要过程感的工具类型
- 结果优先型：主要消费完成态或失败态，适合用户只关心最终产出的工具类型
- 确认优先型：重点消费确认阶段，适合外部动作或高风险动作类型
- 聚合型：需要把多个阶段或多个事件组合成一个更完整的展示
- 资源投影型：围绕某个逻辑资源重建展示，而不是逐条映射事件

这些分类是消费模式分类，不是工具名分类。

### 3. 展示形态可插拔

专属 renderer 的目标不应被限制为“替换一张卡片外观”。

它可以输出：

- 通用卡片
- 紧凑行
- 折叠块
- 富媒体预览
- 统一交付表面
- 或完全不输出可见实体

只要输入边界稳定，这些形态都应被视为同等合法的消费结果。

## 对工具类型的抽象分类

为了避免把架构和具体工具绑死，建议后续讨论时优先使用工具类型，而不是具体工具名。

例如可以使用以下抽象分类：

- 上下文采集型
  特点是阶段多但用户通常不关心细节，适合轻量展示或弱化过程态

- 外部动作型
  特点是确认与结果说明更重要，适合突出确认态和最终结果

- 文件变更型
  特点是过程与结果都可能重要，适合既能表达操作轨迹，也能表达最终差异

- 资源创建型
  特点是用户关注创建出的资源本身，适合由最终交付物主导展示

- 资源更新型
  特点是后续事件可能改变之前资源的当前态，适合围绕逻辑资源做投影重算

- 交互挂起型
  特点是等待用户输入或恢复同一 turn，适合以等待态与恢复态为核心展示

这些分类的意义在于帮助选择消费策略，而不是制造新的硬编码路由表。

## 推荐的收敛方向

在不大改执行主链的前提下，推荐先朝以下方向收敛：

1. 保持执行层事实模型稳定
2. 逐步提供更统一的 presentation event feed
3. 把现有通用卡片体系明确降级为 default renderer
4. 允许 specialized renderer 选择性消费不同阶段，而不是只能替换现有卡片皮肤
5. 让逻辑资源导向的展示逐步通过统一 feed 与投影重算能力接入

## 当前阶段不建议直接做的事

### 1. 不要把展示策略重新压回执行主链

执行层负责产出事实，不负责决定某类 UI 是否存在。

### 2. 不要把可插拔能力缩窄成“注册一个结果卡片”

真正需要开放的是：

- 输入模型
- 消费策略
- 展示形态

而不是只开放某个 widget 槽位。

### 3. 不要持续增加零散的工具名分支

一旦每新增一种展示类型都要沿着主链添加名称判断，短期虽快，长期一定会重新发生架构漂移。

## 最终约束总结

后续涉及 Tool UI、workflow/result 展示、专属 block、富媒体交付与时间线投影的实现，默认应满足以下约束：

1. 执行层必须稳定产出阶段性事实，但不强制每个阶段都渲染成 UI
2. UI renderer 必须拥有消费哪些事实的选择权
3. 通用卡片体系只是默认消费器，不是唯一合法展示实体
4. 专属展示必须优先通过统一消费边界接入，而不是沿主链扩散特例
5. 统一刷新问题应先抽象为“输入事实变化后如何重算展示投影”

只要这五条不被破坏，后续无论扩展哪一类工具展示，都能保持框架边界稳定并尽量避免架构漂移。
