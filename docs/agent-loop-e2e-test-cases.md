# Agent Loop E2E Test Cases

本文档用于人工验证新的多轮 agent loop 主链是否符合预期。

## 测试前准备

1. 打开应用设置页。
2. 确认以下字段已正确配置：
   - `API Key`
   - `Model`
   - `Base URL`
3. 可选：
   - 将 `Tool Execution Mode` 先设为 `Balanced`
   - 清空旧聊天，避免历史消息影响判断

## Case 1: 纯文本直答

目标：验证不需要工具时，turn 能直接结束，不会插入工具消息。

步骤：
1. 新建对话。
2. 发送：`用一句话解释什么是 SQLite`

预期：
1. 聊天中只出现用户消息和最终助手回答。
2. 不出现“准备执行工具”“正在执行工具”“工具结果”卡片。
3. 发送完成后输入框恢复可发送状态。

## Case 2: 单工具自动执行

目标：验证 agent loop 能决定调用只读工具，并在工具结果后给出最终回答。

步骤：
1. 在当前对话里先手动发一条明显可检索的消息，例如：
   - `数据库版本已经升级到 7`
2. 再发送：`我刚才提过数据库版本吗？`

预期：
1. 先出现工具执行过程卡片。
2. 工具结果里能看到与“数据库版本”相关的命中信息。
3. 最终助手回答会基于工具结果进行总结。
4. 最终仍只有一个完整最终回答，不会无限继续。

## Case 3: 多工具串行执行

目标：验证同一个 turn 内可以连续调用多个工具，而不是单轮结束。

步骤：
1. 发送：`先搜索 OpenAI 今天的最新消息，再读取你认为最相关的一篇网页，然后总结给我`

预期：
1. 能看到至少两段工具流程：
   - 一次联网搜索
   - 一次网页读取
2. 工具结果消息顺序正确。
3. 两次工具之后才出现最终回答。
4. 最终回答明确引用前面两个工具步骤的信息。

## Case 4: 需要确认的工具暂停

目标：验证带副作用工具会进入 `awaiting confirmation`，不会直接执行。

步骤：
1. 发送：`提醒我今晚 8 点提交周报`

预期：
1. 出现确认卡片，而不是直接成功。
2. 发送阶段停留在等待确认状态。
3. 在你点击确认前，不会出现“已创建提醒”结果。

## Case 5: 确认后恢复执行

目标：验证确认动作会恢复同一个 turn，而不是新开一轮旧链路。

步骤：
1. 先完成 Case 4，停在确认卡片。
2. 点击继续或确认执行。

预期：
1. 原确认卡片会变成“正在执行工具”。
2. 随后出现工具结果，例如“已创建提醒”。
3. 工具结果后如果模型需要，还会继续补一条最终回答。
4. 不会出现重复的用户消息或重新开始整轮发送。

## Case 6: 取消确认

目标：验证取消会终止挂起工具，并把发送状态复位。

步骤：
1. 再次发送：`提醒我明天上午 10 点开会`
2. 在确认卡片出现后点击取消。

预期：
1. 卡片内容变为“已取消工具执行”或等价状态。
2. 输入框恢复可发送状态。
3. 不会再继续执行工具，也不会补最终回答。

## Case 7: 多步后进入确认

目标：验证先执行一个无副作用工具，再命中一个需要确认的工具时，turn 会在中途暂停。

步骤：
1. 发送：`先帮我回忆我们刚才聊到的数据库 schema，再提醒我晚上同步修复结果`

预期：
1. 先出现一次历史搜索类工具结果。
2. 然后出现提醒类确认卡片。
3. 说明同一个 turn 内已经完成“成功工具 -> 挂起确认”的组合链路。

## Case 8: 失败后仍能收敛

目标：验证工具失败不会把 UI 卡死。

步骤：
1. 构造一个大概率失败的读取请求，例如：
   - `读取这个网页并总结 https://not-a-real-domain-for-agent-loop-test.invalid`

预期：
1. 会出现工具失败或读取失败结果。
2. 页面不会卡住。
3. 输入框最终恢复可发送状态。
4. 如果模型能兜底，可能继续给出失败说明；如果没有，也不应无限 loading。

## 建议记录项

每条 case 建议记录：
1. 是否出现了预期的消息顺序
2. 是否出现重复消息或死循环
3. 工具确认卡片是否可继续 / 可取消
4. 发送完成后输入框是否恢复
5. 是否有明显与旧单轮工具链一致的异常行为
