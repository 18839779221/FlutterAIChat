# FlutterAIChat AI 进阶学习与项目演进计划

## 1. 这份计划为什么要调整

你已经完成了一个明显高于入门水平的 AI Chatbot 项目。根据当前仓库结构和 README，你已经具备以下能力：

- 聊天型 AI 应用的基础产品能力：多会话、多分组、流式输出、消息管理
- 本地数据持久化能力：SQLite 存储、历史记录分页、消息 CRUD
- 一定程度的 AI 应用架构能力：LLM 抽象、工厂模式、上下文策略
- 一定程度的交互体验能力：Markdown 展示、代码块渲染、模式切换

这意味着下一阶段不应该继续把主要时间投入在“再做一个聊天壳子”上，而要开始补下面几类真正决定上限的能力：

- RAG：让应用具备基于资料可靠回答的能力
- Tool Calling / Structured Output：让模型不只会说，还能执行任务
- AI 工程化：让系统可评估、可观测、可降级、可扩展
- 多模态与端侧能力：让你的 Android 背景体现出差异化

一句话总结：

把 FlutterAIChat 从“聊天产品”升级成“移动端 AI 助手系统”。

## 2. 当前项目的能力定位

当前项目更接近以下定位：

- 一个体验较完整的 LLM Chat Client
- 一个具备基础 AI 应用架构雏形的跨端客户端项目
- 一个适合继续向知识库助手、会议助手、开发助手演进的底座

当前项目还没有充分覆盖，或者至少还不是它的核心亮点的能力包括：

- 知识库导入、切片、embedding、检索、引用回答
- 工具调用和结构化结果渲染
- 明确的模型评测机制
- 成本、延迟、失败重试、缓存、降级策略
- 语音、OCR、图像理解
- Android 原生能力和端侧推理能力

所以新的目标不是“继续丰富聊天页面功能”，而是“增加 AI 系统能力”。

## 3. 新的 90 天总目标

90 天结束时，建议你让项目达到下面这个状态：

- 它仍然可以聊天，但聊天不再是唯一亮点
- 它支持至少一个知识库问答场景
- 它支持至少一种工具调用场景
- 它支持至少一种多模态输入场景
- 它形成一套你自己能讲清楚的 AI 工程方案

如果做得比较理想，这个项目可以升级成下面三个方向之一：

- 开发文档问答助手
- 会议纪要与任务助手
- 个人知识库与多模态助手

对你来说，优先推荐的方向是：

开发文档问答助手。

原因：

- 和你的 Android 工程背景天然贴合
- 最容易做出稳定的 RAG 能力
- 最容易在简历和面试里讲清楚业务价值
- 最容易进一步扩展成截图问答、代码问答、文档助手

## 4. 接下来 90 天的核心学习重点

优先级建议如下：

1. RAG
2. Tool Calling / Structured Output
3. AI 工程化
4. 多模态输入
5. Android 原生与端侧能力
6. 模型原理补充

可以降低优先级的内容：

- 继续打磨基础聊天 UI
- 继续围绕 prompt 做很多模式开关
- 过早投入模型微调
- 过早投入复杂 Agent 框架

## 5. 详细的 12 周执行计划

### 第 1 阶段：第 1-4 周
### 目标：把项目从 Chat Client 升级到 Task-oriented AI Assistant

#### 第 1 周：梳理现有架构，补清“AI 工程视角”

学习重点：

- 什么是系统提示词、用户消息、上下文消息的职责边界
- 什么是结构化输出，为什么它比“让模型自由发挥输出 JSON”更可靠
- 什么是工具调用，为什么它是 AI 应用从聊天走向执行的关键
- 为什么 prompt 技巧不是核心壁垒，系统能力才是

建议你在项目里做的事：

- 梳理当前请求链路：输入 -> 上下文拼装 -> 模型请求 -> 流式展示 -> 落库
- 画一张简单时序图，确认每一步责任归属
- 识别哪些逻辑还耦合在聊天流程里，后续要抽出来

建议新增的模块方向：

- `lib/models/tool/`
- `lib/services/tool_call_service.dart`
- `lib/models/response/`
- `lib/widgets/structured_message/`

本周产出：

- 一份项目架构图
- 一份 AI 请求链路说明
- 一份后续改造任务清单

验收标准：

- 你可以不看代码，直接向别人说明消息从输入到输出的完整链路
- 你知道后续要把哪些功能从 `chat_service.dart` 拆出来

#### 第 2 周：做 Structured Output

学习重点：

- JSON Schema 的基本思想
- 结构化输出和普通文本输出的差别
- 为什么结构化输出适合摘要、待办、FAQ、表单生成
- 输出校验和失败兜底机制

建议你先做一个最小场景：

- 让模型把一段长文本总结成结构化卡片
- 输出字段可以是：标题、摘要、关键点、行动项、风险项

建议项目改造：

- 新增结构化响应模型
- 新增结构化消息渲染组件
- 给消息类型增加枚举，比如 `plainText`、`structuredCard`、`toolResult`

本周产出：

- 聊天中可以展示结构化卡片
- 结构化失败时自动回退为普通文本

验收标准：

- 结构化结果可以稳定渲染
- 用户不会看到原始 JSON 垃圾输出

#### 第 3 周：做 Tool Calling

学习重点：

- 工具调用的核心流程：模型决策 -> 参数生成 -> 工具执行 -> 结果回填
- 工具设计原则：输入清晰、输出稳定、幂等、可追踪
- 为什么工具要和 UI 解耦
- 工具调用失败时如何给用户反馈

建议先实现 2-3 个简单工具：

- 从一段对话中提取待办项
- 根据聊天内容生成 FAQ
- 搜索本地对话记录

建议新增模块：

- `lib/models/tool/tool_definition.dart`
- `lib/models/tool/tool_result.dart`
- `lib/services/tool_registry.dart`
- `lib/services/tool_executor.dart`

如果后面准备加后端，这部分也可以迁移到服务端。

本周产出：

- 至少一个可用的工具调用链路
- 聊天结果中能展示“工具已执行”状态

验收标准：

- 模型可以稳定触发工具
- 工具结果可以回注到最终回答里
- 工具失败时界面有明确提示

#### 第 4 周：补 AI 工程基础设施

学习重点：

- 请求日志、错误分类、重试策略、超时机制
- 流式请求失败时如何恢复
- 令牌成本意识
- 常见的 prompt 注入和输出污染问题

建议你为项目加上：

- 统一请求日志
- 请求耗时统计
- 错误类型区分：网络错误、鉴权错误、解析错误、模型错误
- 简单重试策略
- 缓存和去重思路

建议新增模块：

- `lib/models/telemetry/`
- `lib/services/chat_metrics_service.dart`
- `lib/utils/error_mapper.dart`

本周产出：

- 一个最小的可观测体系
- 你知道最常见失败发生在哪一层

验收标准：

- 出错时你能快速判断问题在网络、模型还是解析层
- 请求性能和错误类型有基本记录

### 第 2 阶段：第 5-8 周
### 目标：做出真正有价值的 RAG 能力

#### 第 5 周：理解并跑通最小 RAG

学习重点：

- embedding 是什么
- 为什么要切片
- 为什么召回不是越多越好
- 什么是 topK、chunk overlap、metadata
- 检索和生成的职责边界

你需要先做的不是复杂工程，而是验证链路：

- 文档导入
- 文本切片
- 生成 embedding
- 存储向量
- 用户提问时检索相关片段
- 携带片段让模型回答

建议先从最简单文档类型开始：

- Markdown
- txt
- 你自己的 Android 学习笔记
- 项目接口文档

实现建议：

- 第一版可以先做轻量后端，避免把 embedding 和检索全塞进 Flutter 客户端
- 如果只是快速验证，也可以先用 SQLite FTS 做关键词检索，再迭代到向量检索

本周产出：

- 一条最小可跑通的 RAG 链路

验收标准：

- 你能演示“基于导入文档回答问题”
- 回答比纯聊天明显更贴近资料内容

#### 第 6 周：做知识库管理功能

学习重点：

- 文档生命周期：导入、解析、切片、索引、更新、删除
- 文档元数据的重要性
- 知识库和聊天会话如何关联

建议项目增加以下能力：

- 导入文档页面
- 文档列表页
- 文档状态显示：待解析、已切片、已索引、失败
- 每条回答展示引用片段或引用来源

建议新增模块：

- `lib/models/knowledge/`
- `lib/services/knowledge_base_service.dart`
- `lib/pages/knowledge_base_page.dart`
- `lib/widgets/reference_chip.dart`

本周产出：

- 最基础的知识库管理能力

验收标准：

- 用户可以知道“回答依据是什么”
- 知识库不是黑盒

#### 第 7 周：开始做 RAG 调优与评测

学习重点：

- 如何判断是检索差还是生成差
- 如何构建最小评测集
- 如何比较不同 chunk size、topK、prompt 模板
- 如何判断回答是否引用错资料

建议你建立一个小型评测集：

- 找 20-30 个你熟悉的问题
- 给每个问题准备理想答案或关键事实点
- 比较不同检索策略的效果

建议新增内容：

- `eval/` 目录或者独立仓库保存评测数据
- 一个简单脚本统计回答命中情况

本周产出：

- 一套最小 RAG 评测方法

验收标准：

- 你不是凭感觉说“效果不错”
- 你可以说明为什么某种 chunk 策略更适合当前数据

#### 第 8 周：做 RAG 安全与体验收口

学习重点：

- 无答案兜底
- 引用缺失兜底
- 冲突文档处理
- 用户上传脏数据时如何降级
- prompt 注入的基本防范

建议补齐：

- 没检索到资料时明确提示
- 检索相关性过低时降低模型自由发挥
- 引用展示和点击定位
- 索引失败可重试

本周产出：

- 一个能稳定演示的知识库问答功能

验收标准：

- 不相关问题不会一本正经地胡说
- 回答中能看到资料依据
- 体验可以支撑演示或面试

## 6. 每个主题到底该学到什么深度

### Prompt Engineering

学到这个程度就够：

- 知道 system / user / assistant 角色分工
- 知道少样本示例什么时候有用
- 知道如何约束输出风格和格式
- 知道 prompt 只是系统中的一层，不是唯一核心

不需要投入太多时间在：

- 大量 prompt 黑魔法
- 玄学模板收藏

### Structured Output

你需要真正掌握：

- 如何定义字段
- 如何做输出校验
- 如何设计失败回退
- 哪些业务适合结构化输出

适合拿来练手的任务：

- 会议纪要
- 待办抽取
- 文档摘要
- 风险点提取

### Tool Calling

你需要真正理解：

- 工具不是“让模型更聪明”，而是“让系统更有行动能力”
- 工具接口设计要稳定
- 工具结果要可观测
- 工具执行失败必须可恢复

建议优先练的工具类型：

- 检索工具
- 总结工具
- 本地数据查询工具
- 日历 / 待办写入工具

### RAG

你需要学会的不是名词，而是判断：

- 什么情况下该切大块，什么情况下该切小块
- 什么问题是检索问题，什么问题是生成问题
- 什么数据适合关键词检索，什么数据适合向量检索
- 回答质量差时应该先查哪一层

### AI 工程化

你需要具备这些意识：

- 每个请求都有成本
- 每个失败都要能归类
- 每个关键链路都要能观测
- 每个新能力都要有兜底方案

### 模型原理

你的目标不是研究员级别，而是：

- 理解 Transformer 的基本工作方式
- 理解 embedding、attention、token 的基本概念
- 理解微调、蒸馏、量化分别解决什么问题
- 能和算法同学讲清楚需求与约束

- Embedding 与检索官方指南
- Android 官方 AI / ML 文档
- ML Kit / LiteRT 官方文档
- PyTorch 基础教程
- Hugging Face 关于 Transformer 和 NLP 的入门材料

你阅读这些资料时要带着问题看：

- 这个能力适合客户端做还是服务端做
- 这个能力在当前项目里最自然的接入点在哪
- 这个能力会带来哪些新失败场景
- 它应该如何被评测和观察

## 12. 你下一步最值得做的具体事项

如果你现在只打算先做一件事，建议顺序如下：

1. 给当前项目加 Structured Output
2. 再加 Tool Calling
3. 再做最小 RAG
4. 再做语音或 OCR
5. 最后补 Android 原生差异化能力

如果你现在只选一个最终作品方向，推荐：

开发文档问答助手。

如果你现在只选一个最近两周目标，推荐：

把 FlutterAIChat 升级成“能输出结构化卡片并能调用工具”的任务型 AI 助手。

## 13. 给未来简历和面试的表达方式

你最终不要把这个项目描述成：

“做了一个 AI 聊天项目。”

更好的表达是：

“基于 Flutter 构建了一个具备多会话管理、上下文策略、流式输出、本地持久化的移动端 AI 助手，并逐步演进出结构化输出、工具调用、RAG 知识检索和多模态输入能力。”

如果后面 RAG 和多模态做出来，这个项目的表达会更有竞争力。
