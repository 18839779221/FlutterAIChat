# Flutter Markdown Hybrid Reader 设计

## 背景

当前聊天时间线已经具备较好的 Markdown 基础阅读体验，`FlutterMarkdownImpl` 中也已经对正文、标题、引用、列表、代码块等元素做过定制。上一轮 Markdown 节奏与技术内容块统一改造后，代码块和技术预览的视觉方向已经逐渐收敛。

本轮讨论进一步明确：第一阶段不优先扩展公式、图表、Mermaid 等新格式能力，而是先把 `flutter_markdown` 路径的核心阅读质感打磨到更接近专业文档级。目标是让完成态助手回答看起来像“被认真排版过的短文档”，而不是“Markdown 语法被渲染出来了”。

## 目标

本阶段目标是为 `FlutterMarkdownImpl` 建立一套 Hybrid Reader 阅读规则：

- 让长答案具有稳定、安静、专业的阅读节奏。
- 让技术解释、步骤说明、架构分析等回答更容易扫读。
- 优先打磨标题、正文、列表、引用/旁注四类高频元素。
- 保持当前项目“文档优先、浅色主导、低噪声、信息密度适中”的产品气质。
- 为后续公式、图表、Mermaid、语义块等扩展能力预留一致的阅读底座。

## 非目标

- 不新增公式、图表、Mermaid、callout 等格式能力。
- 不处理 `markdown_widget` 路径的视觉统一。
- 不重做消息列表、输入栏、顶部栏或聊天页整体布局。
- 不改变数据模型、消息持久化、流式协议或上下文架构。
- 不把 Markdown 区域改造成卡片集合或重装饰排版系统。

## 视觉方向

本阶段采用 **Hybrid Reader** 方向。

Hybrid Reader 的含义是：以专业文章式阅读体验为主体，同时保留 AI Chat 中常见技术内容的结构表达。它不追求论文式严肃，也不追求工程仪表盘式高密度，而是在聊天场景里提供一种安静、清晰、可持续阅读的文档面。

具体气质：

- 正文像短文档，可连续阅读。
- 标题像章节锚点，而不是卡片标题。
- 列表像扫读结构，而不是缩进后的普通段落。
- 引用像旁注或提醒，而不是强提示卡片。
- 代码块继续作为正文内嵌的技术内容块，不抢占整个回答的视觉中心。

## 设计原则

### 1. 正文是基准层

正文段落决定整体阅读气质。标题、列表、引用都应围绕正文节奏展开，而不是各自独立定义视觉强度。

正文应保持当前小字号、高信息密度的方向，但通过更稳定的行高和段落节奏降低长时间阅读疲劳。

### 2. 层级主要来自留白和字重

标题不应明显放大到报告标题或营销标题的程度。章节感应主要由前后 padding、相对字号、轻中等字重和与正文的距离共同建立。

### 3. 列表服务扫读

列表的核心价值是帮助用户快速定位要点和步骤。列表缩进需要适合手机宽度，项间距需要比普通段落更利于扫读，但不能让消息过度拉长。

### 4. 引用是旁注，不是卡片

引用块应表达补充、约束、提醒或外部引用。它需要有明确语义，但视觉上应低噪声：轻背景、细竖线、适度 padding、克制圆角。

### 5. 完成态优先，流式态跟随

本阶段主要打磨完成态 Markdown。流式态可以继续使用轻量纯文本，但其字号、行高和左右 padding 应与完成态正文保持近似关系，避免完成前后视觉跳变过大。

## 元素规则

### 正文段落

正文段落是 `FlutterMarkdownImpl` 的默认阅读基准。

建议方向：

- 字号保持在当前 `13px` 左右，不明显放大。
- 行高略偏舒展，适配中英文混排和长句。
- 段落之间依赖全局 block spacing 提供呼吸感。
- `strong` 不应过重，避免中文段落出现粗黑斑块。
- `em` 保持斜体语义，但颜色不额外强调。

验收观感：

- 一段 5 到 8 行的中文解释读起来不挤。
- 多段连续正文不显散。
- 中英文、代码名词、数字混排不明显抖动或断裂。

### 标题层级

标题用于组织长回答，尤其是架构解释、步骤方案、调研总结和对比分析。

建议方向：

- `h1` 很少在聊天回答里出现，应克制处理，作为最高章节标题。
- `h2` 是主要章节标题，需要有最明显的前置留白。
- `h3` 是小节标题，留白略小于 `h2`，但仍需和正文区分。
- 标题字号保持克制，重点通过 padding 和 `FontWeight.w500` 左右的权重建立层级。
- 标题下方距离应小于标题上方距离，让标题自然归属到后续正文。

验收观感：

- 长回答可以快速扫到章节。
- 标题不会像独立卡片标题一样压过正文。
- 连续多个小节不会让消息显得碎。

### 列表

列表是技术回答和方案说明里的高频结构。

建议方向：

- `listIndent` 需要比默认 Markdown 更克制，避免手机上正文宽度被吞掉。
- bullet 颜色使用次级文本色，降低视觉噪声。
- 列表项行高接近正文，但项间距略有区分。
- 有序列表应更适合步骤，无序列表应更适合并列要点。
- 嵌套列表不作为本阶段重点，但基础缩进不能导致窄屏不可读。

验收观感：

- 3 到 6 项列表能快速扫读。
- 列表不显得比正文更拥挤。
- 手机宽度下列表项仍有足够行长。

### 引用/旁注

引用块应从“提示框”方向转为“旁注”方向。

建议方向：

- 保留左侧细竖线作为主要语义提示。
- 背景色比当前技术块更轻，避免形成强卡片。
- padding 稍大于正文段落，但不宜过厚。
- 圆角保持柔和，但不能像独立卡片。
- 引用文字使用次级文本色，强调其补充属性。

验收观感：

- 引用能被一眼识别。
- 引用不会打断正文阅读流。
- 多个引用出现在长回答中时不显得像卡片堆叠。

## Flutter 映射

本阶段主要落点是 [FlutterMarkdownImpl](/Users/skka/flutterSpace/FlutterAIChat/lib/widgets/markdown/flutter_markdown_impl.dart) 中的 `MarkdownStyleSheet`。

建议调整的 style sheet 项：

- `p`：正文基准样式。
- `strong` / `em`：与正文节奏对齐的强调样式。
- `h1` / `h2` / `h3`：克制的标题字号与字重。
- `h1Padding` / `h2Padding` / `h3Padding`：章节节奏的主要控制点。
- `blockSpacing`：所有块级元素的全局呼吸基准。
- `listBullet` / `listIndent`：列表可读性与小屏宽度。
- `blockquote` / `blockquotePadding` / `blockquoteDecoration`：旁注化引用。
- `horizontalRuleDecoration`：低存在感分割线。

本阶段不需要新增消息类型或数据结构。若实现时发现常量散落导致维护困难，可以在 `lib/widgets/markdown/` 下新增仅服务 `flutter_markdown` 的私有 token/helper，例如：

- `flutter_markdown_reader_tokens.dart`
- `HybridMarkdownReaderTokens`

该 token 层只表达当前 `flutter_markdown` 阅读规则，不承担 `markdown_widget` 兼容职责。

## 与现有技术内容块的关系

代码块已经通过 `CodeBlockBuilder` 和 `CodeBlockWidget` 进入共享技术内容块方向。本阶段不重做代码块外观，但需要把代码块放回 Markdown 节奏系统中理解：

- 代码块前后留白应略大于普通段落。
- 代码块不应显得像完全独立模块。
- 代码块顶栏和内容表面继续保持当前浅色技术内容块方向。
- 如果后续新增公式、图表、Mermaid，它们也应作为正文嵌入块，而不是新的大型卡片系统。

## 流式态关系

当前 [StreamingResponseBlock](/Users/skka/flutterSpace/FlutterAIChat/lib/widgets/chat_blocks/streaming_response_block.dart) 使用 `SelectableText` 渲染生成中的文本。它不需要在本阶段变成完整 Markdown 渲染器。

建议原则：

- 流式态保持轻量，优先稳定和性能。
- 流式态正文行高与完成态正文接近。
- 完成态切换到 Markdown 后，视觉节奏可以更精细，但不应出现明显字号或密度突变。

## 后续扩展预留

完成 Hybrid Reader 底座后，再考虑以下能力：

- 公式：行内公式和块级公式作为正文内嵌数学内容。
- 图表：从 Markdown 表格或结构化数据生成轻量图表块。
- Mermaid/流程图：将架构、流程、状态机渲染为可扫读图形。
- 语义块：Note、Warning、Tip、Result、Sources 等 callout。

这些扩展都应复用本阶段建立的阅读原则：嵌入正文、低噪声、手机可读、完成态稳定。

## 验收标准

- 长答案第一眼像被认真排版的专业短文档。
- 标题、正文、列表、引用之间的节奏统一。
- 标题有章节感，但不压过正文。
- 正文长段落可持续阅读，不挤也不散。
- 列表在手机宽度下仍可读，缩进不过度。
- 引用像旁注或提醒，不像强卡片。
- 完成态 Markdown 与流式态纯文本之间没有明显视觉断层。
- `flutter analyze` 与相关 widget 测试通过。

## 风险与缓解

### 风险 1：阅读节奏过松

如果 block spacing 或标题 padding 过大，聊天消息会变长，降低多轮对话效率。

缓解：

- 保持正文字号不明显放大。
- 优先调局部 padding，而不是整体加大所有 spacing。
- 用真实长回答在手机宽度验证。

### 风险 2：标题层级过强

如果标题过大或过粗，回答会像报告或博客页面，破坏聊天场景的轻盈感。

缓解：

- 标题字重控制在轻中等。
- 主要用前后留白建立层级。
- 标题下方间距小于上方间距。

### 风险 3：引用仍然像卡片

引用背景、圆角或 padding 如果过强，会和技术内容块争夺注意力。

缓解：

- 背景透明度保持低。
- 左侧竖线作为主语义。
- 文字颜色使用次级文本。

## 实施优先级建议

1. 先调整正文、标题和全局 block spacing。
2. 再调整列表缩进、bullet 样式和项间距。
3. 最后调整引用为旁注风格。
4. 对比流式态与完成态的视觉差异，必要时微调 `StreamingResponseBlock`。
5. 用真实长回答、步骤列表、引用说明三类样例做截图验证。
