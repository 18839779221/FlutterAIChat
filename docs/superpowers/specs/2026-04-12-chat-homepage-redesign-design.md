# 聊天主页改版设计说明

## 摘要

重做聊天主页面，让它更像一个成熟的 AI 产品，而不是一个在默认 Flutter 聊天页基础上做了些样式美化的界面。

新的方向是一种克制、深色的 `AI 工作台` 聊天界面：

- 沉浸、安静，而不是浮夸
- 通过层级和色调深度体现高级感，而不是依赖渐变
- 为长时间阅读而优化
- 由一个更强的输入区承接核心交互
- 以手机优先，同时保证桌面和 Web 也有明确构图

这份 spec 只聚焦聊天主页，不在这一轮尝试重做整个应用。

## 问题

当前聊天主页虽然在部分组件上已经开始做精修，但整个页面仍然更像一个标准 Flutter 应用骨架，上面再叠加一些局部视觉优化。

目前的主要问题：

1. 页面骨架仍然被传统的 `AppBar + Drawer + 底部输入框` 结构主导。
2. 顶部栏占据了注意力，但并没有明显提升阅读体验。
3. 输入区虽然比之前更好，但仍然更像一个紧凑表单，而不是产品里的主交互面。
4. 消息区更像一组彼此独立的卡片列表，而不是一个统一的阅读系统。
5. 桌面和 Web 端很容易退化成“被拉宽的手机布局”，而不是有明确构图的大屏聊天界面。

## 目标

- 让聊天页呈现沉浸、克制、产品级的体验。
- 尽量增加可见阅读区域，尤其是顶部区域。
- 让 header 成为一层轻量的悬浮控制层，而不是传统顶栏。
- 让输入区成为视觉上更稳、更强的 composer 交互面。
- 将用户消息、助手内容、工具状态和 reasoning 状态统一成一个连贯的聊天系统。
- 在保持手机端高可用性的同时，让桌面和 Web 端看起来是经过设计的。

## 非目标

- 这一轮不重做设置页或其他次级页面。
- 不做强品牌化或偏营销视觉的设计处理。
- 不做大规模动效设计。
- 不替换现有聊天架构或 Riverpod 控制器边界。

## 已确认的设计方向

### 名称

`Tonal AI Workbench`

### 为什么适合

这个方向比“纯阅读器 UI”或“夸张的 AI 未来感风格”更适合一个成熟的 AI 聊天产品。

它强调：

- 深色，但不是纯黑
- 精确层级，而不是装饰感
- 面向长文本阅读的安静稳定感
- 一个真正像工作区的输入面
- 足够承载 tool-call 和 reasoning 的系统气质

## 设计原则

- 内容优先，装饰次之。
- 页面应该像一个连续的阅读表面，而不是几个硬切分区块。
- header 应尽可能少占用阅读空间。
- composer 应该比 header 更强、更稳。
- 层级优先通过间距、表面层次和字体建立，而不是先靠颜色强调。
- 工具、reasoning、加载、流式输出等状态都应被整合进同一系统，而不是像外挂层。
- 大屏必须重新组织构图，而不是简单拉伸。

## 体验模型

页面整体应该像一个专注的 AI 工作空间：

- 顶部边缘是轻的、安静的
- 中间是一条稳定的阅读轨道
- 底部是一个有信心的交互停靠区

用户应感受到这个界面是为长时间思考和对话而设计的，而不是为了快速消息往返。

## 结构性改版

### 1. 基础阅读表面

页面根层应变成一整张连续的深色阅读面，而不是由几个明显的 app 区块拼起来。

含义：

- 避免视觉上很强的顶部 app bar
- 避免消息区和 composer 之间出现明显硬接缝
- 通过色调深浅和间距建立层级

### 2. 悬浮 Header 层

header 应变成一层轻薄的悬浮控制层，而不是标准 app bar。

推荐行为：

- 左右两侧只放必要操作
- 中间区域默认保持镂空
- header 漂浮在阅读表面上方，但视觉重量很低
- 只有在提升可读性时，才允许使用非常克制的半透明或模糊背景
- 在滚动后，header 可以略微增强存在感，但始终不能成为页面最抢眼的区域

这是一个 `Ghost Header`，不是装饰性的玻璃拟态顶栏。

### 3. 阅读轨道

消息应被组织在一条稳定的内容轨道上，拥有更克制的宽度和更平稳的垂直节奏。

含义：

- 各类消息表面应该属于同一个系统
- assistant 内容应更接近文档阅读面
- user 消息仍然右侧锚定，但不能有玩具感
- turn 与 turn 之间的间距，应明显大于内部子块之间的间距

### 4. 锚定式 Composer

composer 应成为页面的主交互停靠区。

含义：

- 它应像一个稳定停靠在底部上方的交互表面，而不是一个简单描边输入框
- 它需要和阅读轨道对齐
- 发送、模式切换、helper text 都应该属于同一个 composer 系统
- idle、streaming、awaiting confirmation、executing tools 等状态都应该通过 composer 被统一表达

### 5. 有完成度的空状态

当没有消息时，页面也应该是“设计过的”，而不是空白或脚手架式占位。

空状态应当：

- 保持与聊天主页一致的色调氛围
- 提供一个克制、安静的开始邀请
- 可选地提供少量建议 prompt
- 避免 demo 占位感

## Header 设计说明

### 角色

header 的职责是提供轻量的方向感和访问入口，而不是承担强品牌或强导航栏角色。

### 默认构成

- 左侧：drawer 或 session 入口
- 右侧：新建对话，以及更多操作或上下文动作
- 中间：默认留空

### 可选的自适应行为

当聊天历史足够长，或者用户已经滚离最新消息时：

- 允许中间区域或上层轨道中，轻微出现标题感或当前会话身份感
- 但它必须始终从属于阅读内容

### 视觉处理

- 低透明度深色表面，或轻度模糊承托层
- 不使用高亮强调色背景
- 不使用渐变 hero 区
- 图标操作区应有一致的形状和克制的填充感

## 消息系统说明

### 消息语言

消息区应该表现为一个对话系统里的不同语气层，而不是一组互相独立的小组件。

### 用户消息

- 右侧锚定
- 比 assistant 表面更扎实一点、更收一点
- 紧凑但不能显得小气
- 与 assistant 表面在圆角和边界逻辑上保持同源

### 助手消息

- 作为主要长文本阅读面
- 表面反差低于 user bubble
- 内边距更舒展，边缘更平静
- 优先服务 markdown 阅读舒适度

### Reasoning / Tool / Structured Blocks

- 必须继承自 assistant 内容同一表面家族
- 差异应来自色调层级、标签方式和内部布局，而不是另一套组件语言
- 不能像第三方卡片被硬塞进聊天页

### 节奏

- turn 与 turn 之间的间距应大于内部 block 间距
- 内部 block 之间的节奏应重复、稳定、低噪声
- 标签和元信息不能压过正文内容

## Composer 说明

### 角色

composer 是整个产品最重要的交互面。

### 必须具备的特质

- 视觉上被锚定
- 反复使用仍然舒适
- 有信心，而不是小而弱
- 在 idle 和处理中状态下都保持统一

### 结构

- 外层停靠表面
- 内层输入区域
- 附着的次级控制区

### 交互说明

- helper/status 文案应像低噪声上下文提示，而不是调试条
- 模式 chip 应像整合进 composer 的切换器，而不是遗留的工具 pill
- 发送动作必须明显是主操作
- streaming 和 tool 状态应保持冷静、清晰、可读

## 跨平台构图

### 手机

- 优先保证拇指可达性和重新进入输入的低阻力
- header 必须尽可能紧凑
- 滚动后也应容易回到 composer

### Desktop 和 Web

- 避免消息内容全宽铺开
- 保持稳定的中央阅读轨道
- composer 宽度和阅读轨道严格对齐
- 在空间允许时，让 session 导航自然升级成更明确的 side rail

## Flutter 映射

### ThemeData 与颜色角色

需要让页面从默认 Material 骨架样式，转向聊天页专用的表面语义。

建议的表面角色包括：

- 页面背景
- 悬浮 chrome 表面
- 阅读表面
- 强化阅读表面
- composer 停靠表面
- 激活强调表面

应结合 `ColorScheme` 和 `ThemeExtension` 一起使用，而不是在 widget 中散落单次颜色定义。

### Typography

建立更平静、更适合聊天阅读的字体层级：

- 页面与控制标签：紧凑但不小气
- 元信息与 chip：次级层
- 消息正文：比当前更易读、更舒展
- 长文本 assistant 内容：优先可扫描性

不要仅靠颜色来解决层级问题。

### Spacing

需要比当前更有高级感的垂直节奏。

同一套 spacing 逻辑应同时约束：

- 页面外边距
- turn 间距
- block 间距
- composer 内边距
- header 控件间距

### Shape

需要一套一致的圆角体系，覆盖：

- header 按钮
- user 消息
- assistant 表面
- tool workflow 卡片
- composer 外壳

不能让每个区域各自发明自己的轮廓语言。

### 可复用 Widget

更推荐新增或收敛出一批聊天页专用 widget，例如：

- `ChatShellScaffold`
- `ChatFloatingHeader`
- `ChatReadingRail`
- `ChatComposerSurface`
- `ChatEmptyState`
- `ChatSessionRail`

这些名字是方向性建议，不是必须锁死的 API。

## 实施优先级

### 优先级 1：聊天页骨架与布局层级

最先改：

- 页面 scaffold 结构
- floating header 处理
- 消息轨道宽度与 padding
- composer 锚定方式

在这一步完成前，不应先去打磨单个消息卡片。

### 优先级 2：消息系统统一

然后细化：

- user bubble 的处理方式
- assistant 文档块与 final response 表面
- tool workflow 与 structured output 的整合感
- 消息间距节奏

### 优先级 3：空状态与 session 导航

最后完善：

- 空状态质量
- drawer 或 rail 的视觉语言
- 桌面端的专属构图

## 验收标准

当满足以下条件时，说明这次改版在方向上成功：

- 页面不再像默认 Flutter app shell
- header 足够轻，并显著保留了阅读面积
- composer 成为最强的主交互面
- 消息区呈现统一系统感，而不是碎片化卡片堆叠
- 深色模式通过色调深度体现高级感，而不是靠渐变
- 桌面和 Web 端看起来是经过构图设计的，而不是拉宽手机页

## 风险

- 如果模糊和半透明使用过度，会变成装饰噪声。
- 如果保留现有 scaffold 结构过多，可能无法带来真正的提升。
- 如果 composer 做得太厚，会挤压手机端阅读空间。
- 如果在重新定义布局层级前就先打磨消息卡片，可能会浪费精力。

## 首轮实施边界

第一轮 UI 改动应包括：

- 聊天页骨架重组
- floating header
- 阅读轨道优化
- composer 重做
- 空状态重做
- drawer / session 表面降噪

第一轮不应扩展成整个应用的全面改版。

## 后续

实现完成后，应使用 `flutter-ui-review` 对聊天主页结果进行严格评审，判断剩余问题属于方向级问题，还是只剩下 polish 级问题。
