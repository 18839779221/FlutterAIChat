# 最新消息底部连续运行状态尾注增量设计

## 背景

上一版设计已经将运行状态从输入框顶部迁移到了最新消息块底部，但仍存在两个关键问题：

1. 状态提示可能在一个 `turn` 尚未结束时中断
2. 尾注样式仍然偏组件化，存在轻微“块感”或边框感

另外，运行文案如果一味追求具体，也会在工具并行场景下带来误导。例如同时存在 `web_search` 和 `fetch_webpage` 时，如果尾注只显示“正在读取网页”，用户会误以为系统只在做这一件事。

因此，本次需要在“持续显示”“系统动作视角”“并行安全”之间做更稳的平衡。

## 目标

在不改变现有 tool / turn 生命周期语义的前提下，让最新消息底部尾注满足以下要求：

- 只要当前 `turn` 尚未结束，尾注就尽量不间断显示
- 文案优先采用系统动作视角，而不是泛泛的“正在处理”
- 单工具动作明确时展示具体动作
- 多工具并行或主动作不明确时退化为稳定的抽象文案
- 尾注进一步去卡片化，不要边框感

## 非目标

本次不处理以下内容：

- 不新增多条并行状态列表
- 不把多个工具的执行详情塞进尾注
- 不新增全局悬浮状态层
- 不重做 tool card 本体的运行态 UI
- 不重建 send phase / turn phase 底层状态机

## 核心设计

### 1. 尾注按 `turn` 级持续存在

尾注的显示条件不再仅仅依赖某一瞬时 phase 是否命中，而是依赖“当前发送事务 / 当前 turn 是否仍在运行”。

规则：

- `turn` 开始后，只要尚未完成、失败、取消或进入真正结束态，尾注应持续存在
- 中间即使具体状态源短暂切换，也不应立刻消失
- 只有当这一轮真正结束时，尾注才整体移除

这意味着尾注表达的是“本轮仍在运行”，而不是“当前瞬时 phase 刚好有文案可显示”。

### 2. 文案使用系统动作视角

文案应描述系统当前在做什么，而不是从用户任务结果角度描述。

推荐文案类型：

- 正在请求模型
- 正在规划下一步
- 正在执行工具
- 正在联网搜索
- 正在读取网页
- 正在读取文件
- 正在列出目录
- 正在搜索文件内容
- 正在生成回复
- 正在等待结果

其中：

- “正在处理”不作为常规文案
- 仅在极端空窗期，允许使用更具体的保底文案“正在等待结果”

### 3. 文案按“最具体且不误导”的原则选择

文案来源优先级从高到低如下：

1. **单一明确工具动作**
2. **模型阶段动作**
3. **保底文案**

#### 3.1 单一明确工具动作

当且仅当当前工具动作明确、且不会因并行而误导用户时，才显示具体 tool 文案。

例如：

- 正在联网搜索
- 正在读取网页
- 正在读取文件
- 正在列出目录
- 正在搜索文件内容

#### 3.2 并行工具场景

如果同时存在多个活跃工具，或当前无法稳定判定“唯一主动作”，则不显示某个具体工具文案，而统一退化为：

- 正在执行工具

这样可以避免错误强调某一个工具。

#### 3.3 模型阶段动作

当系统尚未进入具体工具动作，或当前阶段本质是模型工作时，显示：

- 正在请求模型
- 正在规划下一步
- 正在生成回复

#### 3.4 保底文案

如果当前 `turn` 仍在运行，但暂时拿不到足够明确的工具或模型动作语义，则短暂显示：

- 正在等待结果

此文案仅用于桥接空窗，不应成为主流常态。

## 文案映射建议

### 模型阶段

- 用户点击发送后，provider / planner 请求尚未返回：`正在请求模型`
- planner 正在做下一步决策：`正在规划下一步`
- final answer 正在流式输出：`正在生成回复`

### 工具阶段

#### 单一工具明确时

- `web_search`：`正在联网搜索`
- `fetch_webpage`：`正在读取网页`
- `Read`：`正在读取文件`
- `LS`：`正在列出目录`
- `Grep`：`正在搜索文件内容`
- `Glob`：`正在查找文件`

#### 多工具并行或主动作不明确时

- 统一为：`正在执行工具`

### 空窗桥接

- 当前 `turn` 仍运行，但没有更具体状态：`正在等待结果`

## 并行场景规则

这是本次增量设计的核心约束。

### 规则 1

如果只有一个活跃工具，可显示具体工具动作。

### 规则 2

如果有多个活跃工具并行执行，不显示任何单一具体工具动作，而统一显示：

- `正在执行工具`

### 规则 3

如果最新消息块是某个具体工具卡片，但后台同时还有其他工具也在运行，仍以“并行安全”为优先，退化为：

- `正在执行工具`

不要因为“最新消息块恰好是某个工具卡片”就错误暗示系统只在做这一件事。

## 连续性规则

### 1. 不允许无故闪断

在一个 `turn` 内，只要系统还在运行，尾注就不应该因为瞬时状态数据缺口而消失。

### 2. 文案可以变化，但尾注本体不消失

允许尾注中的文案从：

- 正在请求模型
- 正在规划下一步
- 正在执行工具
- 正在生成回复

这样逐步切换，但容器本身应持续存在。

### 3. 短暂状态缺口时保留上一个稳定文案

如果实现成本可控，推荐在短时间状态缺口中优先保留上一条稳定文案，而不是立刻降级。

若当前阶段无法安全保留上一条文案，再退化到：

- 正在等待结果

## UI 风格调整

### 目标

尾注要更像“最新消息的动态脚注”，而不是一条新插入的卡片组件。

### 样式要求

- 不要边框
- 不要明显独立底色块
- 不要卡片化容器
- 保留小状态点
- 保留很淡的刀光
- 刀光只做提示，不形成块状轮廓

### 推荐结构

- 一行水平布局
- 左侧状态点
- 右侧系统动作文案
- 整体贴近消息底部基线

### 动效要求

- 状态点轻微脉冲继续保留
- 刀光比当前更轻、更像掠过文本区域
- 不增加新的闪烁元素

## 数据来源建议

不新增新状态机，但增加一个专门的“尾注文案解析器”来整合现有状态。

建议新增类似：

- `LatestMessageRunningStatusResolver`

职责：

- 根据当前 `turn` 是否仍活跃决定是否展示尾注
- 根据 `sendPhase`、最新 tool steps、活跃工具数量，解析出最稳妥的系统动作文案
- 在并行场景下自动退化为 `正在执行工具`

不负责：

- 渲染
- 消息块布局
- 动效实现

## 推荐解析顺序

1. 当前 `turn` 是否仍活跃
  - 否：不显示尾注
2. 是否存在活跃工具
  - 有多个：`正在执行工具`
  - 有且仅有一个：尝试映射具体工具动作
3. 是否处于模型请求 / 规划阶段
  - 是：显示模型动作文案
4. 是否处于流式生成阶段
  - 是：`正在生成回复`
5. 兜底
  - `正在等待结果`

## 验收标准

- 一个 `turn` 开始后到结束前，尾注尽量持续存在，不应中断
- 单工具明确执行时，尾注显示具体系统动作文案
- 多工具并行时，尾注稳定退化为 `正在执行工具`
- 不出现明显误导性的单工具文案
- 尾注进一步去块化，无边框感
- 执行结束后尾注整体消失

## 风险与注意事项

- 如果文案来源散落在 UI 各层，会很快变得不可维护
- 如果并行判断不准确，会错误暴露具体工具动作
- 如果视觉去底色过头，尾注可能变得不易感知
- 如果连续性策略做成“文案也锁死不变”，则会丢失阶段感；应保证“尾注持续存在，文案可切换”

## 结论

本次增量采用“`turn` 级持续尾注 + 系统动作视角文案 + 并行退化为 `正在执行工具` + 去边框化尾注”的方案。它的目标不是展示更多调度信息，而是在整个 `turn` 生命周期里，用稳定、克制、尽量具体且不误导的方式，让用户持续感知系统仍在运行。
