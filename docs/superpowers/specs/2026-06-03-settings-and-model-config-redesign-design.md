# 设置页与模型配置重构设计

## 1. 背景与目标

当前设置页与模型配置存在以下问题：

- 设置页职责混杂，把运行时选择、模型维护、工具偏好、界面偏好堆在同一长页中
- 顶部存在纯展示型卡片，占据空间但不承载关键动作
- 模型配置页延续了“后台管理面板”式结构，首次用户路径不清晰，日常用户切换成本也偏高
- 首页缺少对“尚未配置模型”的强提示，外部用户下载应用后无法自然进入第一步
- 视觉层级偏弱，整体显得简陋，不够贴合当前主题语言，也缺少专业感与设计感

本次重构目标：

- 将首页、设置页、模型配置页的职责重新拆分清楚
- 将 provider / model 的高频切换从设置页迁移到首页输入区第二行
- 保留统一的模型配置入口，但不新增独立向导页面
- 重做模型配置页结构，以 provider 为单位管理，模型探测为主路径，手动增删 model 作为兜底
- 在不改变核心数据结构和选择逻辑的前提下，显著提升整体专业感、完成度与主题一致性

## 2. 设计原则

### 2.1 信息架构原则

- 首页负责发现问题与高频轻操作
- 设置页负责摘要与入口，不承载高频切换
- 模型配置页负责首次配置与后续维护

### 2.2 交互原则

- 高优先级路径尽量短：首次用户应尽快进入模型配置页，已配置用户应尽快完成 model 切换
- provider 是管理单位，model 是选择单位
- 模型探测是主路径，手动新增 model 仅作兜底能力
- 删除、编辑、设默认等行为保持清晰直接，不做复杂嵌套交互

### 2.3 视觉原则

- 延续当前应用的静态、克制、专业的主题氛围，不引入花哨或装饰性过强的视觉手法
- 用更强的排版、间距、表面层级和控件权重建立专业感，而不是依赖大面积说明卡或杂乱按钮
- 设置与配置相关页面应更接近“安静的控制台”，而不是“传统后台表单页”
- 保持与当前聊天页主题一致的色彩、圆角、表面材质和浮层语言

## 3. 目标用户与场景

### 3.1 首次用户

首次下载应用，没有任何内置模型配置。用户进入首页后需要明确知道：

- 当前无法直接开始对话
- 需要先配置 API Key / Provider / Model
- 应该从哪里进入配置

### 3.2 已配置用户

已配置用户更关注两个动作：

- 在聊天主界面快速切换模型
- 在单独页面中维护 provider 配置、探测模型、做简单编辑删除

## 4. 总体信息架构

### 4.1 首页

首页承担两个职责：

- 未配置状态下承接首次配置提醒
- 已配置状态下提供高频 model 轻切换入口

### 4.2 设置页

设置页承担摘要与入口职责：

- 展示当前模型接入状态
- 提供进入模型配置页的入口
- 保留工具、Skills、Workspace、界面偏好等配置分组

设置页不再承担 provider/model 的日常切换。

### 4.3 模型配置页

模型配置页承担统一配置职责：

- 首次用户从这里完成接入
- 已配置用户从这里维护 provider
- 探测 model、设默认 model、删除 model、编辑 provider 都在此完成

不新增独立 onboarding 页面。

## 5. 首页重构设计

### 5.1 未配置状态

当用户尚未完成模型接入时：

- 用首次配置引导卡覆盖当前推荐案例区域
- 输入框仍然可见，但视觉权重降低
- 输入区第二行左侧显示 `未配置模型`

引导卡只保留最必要的信息：

- 标题：提示尚未配置 API Key / 模型
- 一段简短说明：配置后才能开始对话
- 主按钮：`去配置模型`

点击引导卡主按钮，进入模型配置页。

### 5.2 已配置状态

完成模型接入后：

- 首页恢复原有推荐案例区域
- 输入区第二行左侧显示当前 `Model`
- 用户可在首页直接进行高频 model 切换

### 5.3 输入区第二行的 Model 入口

入口形式：

- 单个轻量胶囊
- 仅展示当前 `Model`
- 位于 token 用量显示左侧

点击后弹出 model 选择 sheet，交互规则如下：

1. 优先展示当前 provider 下的 model 列表
2. 用户可直接点击某个 model 完成切换
3. sheet 底部提供次级入口：`切换 Provider`
4. 点击后进入 provider 列表
5. 选择 provider 后，返回该 provider 的 model 列表，再完成 model 选择

该交互复用当前 provider/model 选择逻辑，不引入新的状态来源。

## 6. 设置页重构设计

### 6.1 页面定位

设置页从“混合操作页”改成“控制入口页”。

重构后保留四个主分组：

1. 模型与连接
2. 当前对话
3. 工具与 Skills
4. 界面偏好

### 6.2 移除项

以下内容从设置首页移除：

- 顶部纯展示卡片
- 当前 provider 的直接切换按钮
- 当前 model 的直接切换按钮
- 过度解释性的长段说明

### 6.3 模型与连接分组

此分组仅展示摘要与入口，建议包含：

- 当前默认 Provider
- 当前默认 Model
- 最近一次测试结果或连接状态摘要
- `进入模型配置`
- `测试当前模型`

不在设置页首页直接做 provider/model 的频繁切换。

### 6.4 其他分组

`当前对话`：

- 保留 workspace 相关设置

`工具与 Skills`：

- 保留工具自动化策略
- 保留 trusted tools 白名单
- 保留 Skills 安装与启停

`界面偏好`：

- 保留主题切换
- 仅保留真实生效、用户可感知的界面级选项

对于当前已有设置项，需要在实现前逐项核实：

- `自动显示键盘`：如果当前没有稳定生效路径或用户无法感知差异，则直接删除
- `清除缓存`：如果仍处于待补充或没有实际效果，则直接删除

界面偏好分组不保留“占位型设置”或“看起来像设置但实际上无效”的条目。

整体视觉上要统一收敛，减少厚重卡片和重复边框。

## 7. 模型配置页重构设计

### 7.1 重构原则

- 不沿用当前页面结构
- 不做 provider 卡片内堆叠大量 model block 和按钮
- 以 provider 为单位管理
- 让模型探测成为默认主路径
- 手动新增/删除 model 只保留为兜底能力
- 编辑和删除尽量简单

### 7.2 页面结构

模型配置页分为三个主要区域。

#### 7.2.1 顶部状态区

用于表达当前接入状态，而不是展示装饰信息。

建议展示：

- 当前默认 Provider
- 当前默认 Model
- 当前接入状态

主操作：

- `新增 Provider`
- `测试当前模型`

如果尚未配置成功，应明确显示“尚未完成模型接入”。

#### 7.2.2 Provider 列表区

列表页只关心 provider 层级，不直接承载复杂 model 操作。

每个 provider 条目展示：

- Provider 名称
- Base URL
- 模型数量
- 默认标记
- 简短状态摘要

每项仅保留极少量操作：

- `编辑`
- `删除`

点击 provider 条目，进入 provider 详情页。

#### 7.2.3 Provider 详情页

该页是本次重构重点，分为两部分。

第一部分：连接配置

- Provider 名称
- Base URL
- API Key

主操作：

- `保存`
- `探测模型`

第二部分：模型列表

- 优先展示探测得到的 models
- 每个 model 行只保留必要操作

每个 model 项包含：

- model 名称
- model id
- `设为默认`
- `删除`

列表底部提供弱化入口：

- `手动新增模型`

这不是主路径，不应作为主视觉按钮强化。

### 7.3 首次配置路径

首次用户进入模型配置页后的路径：

1. 点击 `新增 Provider`
2. 填写 Provider 名称、Base URL、API Key
3. 点击 `探测模型`
4. 从返回结果中选择默认 model
5. 返回首页

该路径不依赖新向导页面。

### 7.4 日常维护路径

已配置用户的典型维护路径：

- 修改 API Key / Base URL
- 再次探测模型
- 删除失效 model
- 手动补充 model
- 设定新的默认 model

所有动作都通过 provider 详情页完成。

## 8. 视觉语言与专业感要求

### 8.1 总体方向

视觉方向命名为：`Quiet Control Surface`

目标气质：

- 安静
- 专业
- 凝练
- 有设计感但不过度装饰

### 8.2 视觉策略

- 使用更明确的标题层级和更克制的辅助文案
- 将主按钮数量压到最少，避免一屏出现大量同权重操作
- 用表面层级、间距节奏和排版密度建立秩序感
- 保持与聊天主界面相同的主题语义色与材质风格
- sheet、卡片、分组、列表项的圆角与表面语言统一
- 删除无价值的解释型文案，尤其是“主题介绍”“设置理念说明”这类不直接帮助用户完成操作的描述

### 8.3 明确避免

- 纯展示型头图卡片
- 一页内堆叠太多相同层级的按钮
- 表单字段、说明文字、状态标签互相争抢注意力
- 传统后台式“粗边框 + 重卡片 + 密集操作条”
- 与现有主题割裂的配色或强调方式
- 主题区域保留大段“无用描述”而缺少实际选择效率

## 9. 状态与逻辑边界

### 9.1 复用现有逻辑

以下逻辑尽量复用：

- provider / model 持久化结构
- `selectProviderAndModel` 选择逻辑
- 当前默认 provider/model 的存储逻辑
- 当前模型测试能力

### 9.2 新增逻辑

需要新增或增强的逻辑包括：

- 首页“未配置模型”状态判断
- 首页引导卡显示/隐藏规则
- 输入区 model 选择 sheet
- provider 详情页中的模型探测能力
- 探测结果写入 provider models 的流程

### 9.3 状态约束

- 首页 model 入口只负责切换，不负责完整管理
- 设置页只负责摘要与入口，不负责高频切换
- 模型配置页负责统一管理，不再拆出单独向导

## 10. 测试与验收点

### 10.1 首页

- 未配置时推荐案例是否被引导卡替换
- 已配置后引导卡是否自动消失
- 输入区第二行是否正确显示 `未配置模型` 或当前 model
- model sheet 是否按“先 model、后 provider”路径运行

### 10.2 设置页

- 顶部纯展示卡片已移除
- 设置页首页不再提供 provider/model 直接切换
- 模型与连接分组是否能正确展示当前摘要状态
- 进入模型配置页与测试当前模型入口是否可用
- `自动显示键盘` 与 `清除缓存` 若无真实效果，应已从设置页删除
- 主题区域不再保留冗长、无操作价值的说明文字

### 10.3 模型配置页

- 可新增 provider
- 可编辑 provider
- 可删除 provider
- 可探测 models
- 可设默认 model
- 可手动新增 model
- 可删除 model

### 10.4 视觉验收

- 设置页与模型配置页是否贴合当前主题而非另起一套风格
- 页面是否明显比当前版本更简洁、更专业
- 主操作与次级操作是否层级清晰
- 首页、设置页、模型配置页三者职责是否一眼可懂

## 11. 非目标

本次不包含以下内容：

- 新增独立 onboarding / 向导页
- 重构 provider/model 的底层数据结构
- 改写当前选择逻辑为全新状态系统
- 引入面向小白用户的复杂解释式流程
- 与本次目标无关的大规模设置系统重写

## 12. 后续实施建议

实施顺序建议如下：

1. 先重构模型配置页的信息架构与视觉结构
2. 再将首页输入区第二行接入新的 model 选择入口
3. 再替换首页推荐案例区域的首次引导卡
4. 最后清理设置页，把模型切换逻辑迁出，仅保留摘要与入口

这样可以先完成核心配置面，再逐步完成首页和设置页的职责迁移。
