# 聊天消息列表动态底部 Inset 设计

## 摘要

当前聊天页的消息列表与底部输入区采用重叠布局：

- `ChatMessageList` 占满主视口
- `ChatInput` 作为底部浮层覆盖在消息列表之上

这种结构要求消息列表始终保留一个稳定的底部安全距离，否则最后一条内容会在视觉上贴进输入区下方。最近版本里，`ChatMessageList` 在检测到底部 overlay 后，把底部 inset 收缩成了接近 `spacing.sm` 的浅间距，导致：

- 最新消息离底部的安全距离不足
- 发送新消息后，最新用户消息不会顶到 header 下方
- assistant 流式回复时，列表缺少一套自然的“从顶部锚定逐步回落到底部安全区”的机制

本设计只解决这一次明确要求的滚动行为，不引入新的复杂滚动模式或显式状态机。

## 目标

### 行为目标

- 消息列表在任何时候都保留稳定的最小底部安全距离。
- 用户发送一条新消息后，该条用户消息所在的最新消息块立即贴到 header 按钮区域下方。
- assistant 开始流式回复后，最新对话区域可以自然向下“填满”视口；动态底部 inset 只允许减小，不允许重新增大。
- 用户手动滚动、消息块自身增高、流式内容增长，都走同一套收缩逻辑，不再引入额外的退出/恢复状态。

### 架构目标

- 不改 `ChatPage` 的主布局结构，继续保持“列表全高 + 底部浮层覆盖”的现有页面模式。
- 不改消息投影模型，不新增 planner / transcript / session context 语义。
- 变化集中在 `chat_ui_providers.dart` 和 `chat_message_list.dart`，避免把滚动规则散落到 controller 或 page 级逻辑。

## 非目标

- 不实现“用户手动查看历史消息时，自动补顶部 inset”的策略。
- 不实现新的“回到底部”按钮或自动追踪模式切换状态机。
- 不改变历史加载锚点保持逻辑。
- 不改 header 结构、输入框结构、overlay veil 视觉样式。

## 现状问题

当前 `ChatMessageList` 的底部 inset 逻辑为：

- 有底部 overlay 时：`spacing.sm`
- 没有底部 overlay 时：`spacing.xl * 4.2`

这会导致底部 overlay 存在时，列表虽然仍在技术上延伸到页面底部，但最后一条内容几乎没有稳定安全距离。与此同时，列表没有“发送后把最新用户消息锚定到顶部”的一次性定位逻辑。

## 方案

### 1. 固定最小底部安全距离

`ChatMessageList` 需要恢复一个稳定的 `minBottomInset`。

它的职责是：

- 始终保证最后一条内容不会紧贴输入区下缘
- 作为动态 inset 收缩的下限

这个 `minBottomInset` 在 overlay 存在时仍保持固定值，不再退化成接近 0 的浅 padding。

### 2. 发送后的“一次性顶置”

当最新用户消息入列后：

- 找到该用户消息所在的最新用户块
- 测量该块当前顶部与“header 下边界目标线”的差值
- 将这个差值转成一段 `extraBottomInset`
- 同步补一个等量 scroll offset，使该用户块立刻移动到目标线

这里的目标线使用现有列表顶部 padding 所定义的可视起点，不新增单独的 header 测量组件。

### 3. 后续阶段只做单调收缩

初始化顶置完成后，不再维护“自动态 / 用户打断态 / 恢复态”等显式状态。

后续每次滚动或布局变化时，只做一件事：

- 读取“最后一个时间线内容块距离底部安全线的实际剩余距离”
- 如果这个距离小于当前 `extraBottomInset`，就把 `extraBottomInset` 缩小到该值
- 如果这个距离更大，则保持不变

这样得到的性质是：

- assistant 回复增长时，底部剩余距离自然变小，`extraBottomInset` 只会收缩
- 用户手动滚动时，如果它改变了内容到底部安全线的距离，也仍然走同一套收缩逻辑
- 由于 `extraBottomInset` 永远不增加，所以不会出现轻微上下滚动后又把消息重新顶回顶部的闪动

### 4. 底部总 inset

列表最终使用的底部 inset 为：

`minBottomInset + extraBottomInset`

其中：

- `minBottomInset` 是稳定下限
- `extraBottomInset` 只在一次发送后的过渡阶段存在，并且单调减小到 `0`

## 测量点

### 顶部锚点

顶部锚点直接复用 `ChatMessageList` 现有的顶部 sliver padding。

原因：

- 它已经承担“为 ghost header 留出可读空间”的职责
- 相比重新量 header widget，这个目标线更稳定，且与当前布局契约一致

### 目标用户块

只给“当前最新用户块”注入可测量 key。

不需要给所有 row 都分配 `GlobalKey`，避免增加不必要的布局成本。

### 底部收缩依据

底部收缩不读抽象的“发送状态”，而是直接读“最后一个时间线块相对底部安全线的实际距离”。

因此：

- 消息块自己变高会触发同一逻辑
- 滚动位置变化会触发同一逻辑
- 不需要区分“这是用户拖动导致的”还是“这是流式增长导致的”

## 风险与约束

### 1. 初始化顶置不能只改 padding

仅增大底部 inset 不会自动把当前可见内容推到顶部目标线，还必须同步补一段 scroll offset。

因此初始化必须是：

1. 计算需要的 `extraBottomInset`
2. 更新 inset
3. 在下一帧把 scroll offset 补到新的目标位置

### 2. 收缩只能减不能增

这条规则是本设计稳定性的关键。

如果允许动态 inset 增大，则会在以下场景出现明显反复：

- 用户轻微上下滑动
- assistant 块重排
- 一次布局抖动后再次测量

因此实现上必须显式保证：

- 新值只能 `<=` 旧值

### 3. 只处理最新用户消息触发的顶置

assistant、tool、历史加载都不触发新的“顶到 header 下方”初始化。

这样可以避免：

- 流式更新期间重复顶置
- 新消息块切换时反复抢滚动

## 测试策略

需要补两类回归：

### 页面级布局测试

- overlay 存在时，底部 padding 不再退化到 `spacing.sm`
- 列表仍然延伸到底部 overlay 之下，保持原有重叠布局契约

### 消息列表行为测试

- 最新用户消息入列且处于发送中时，该用户消息块顶部贴近 header 下方目标线
- assistant 内容增长后，底部总 inset 只会减小，不会反弹增大

## 结论

本设计采用“一次性顶置 + 单调收缩动态 inset”的最小方案：

- 不引入复杂状态机
- 不新增滚动模式
- 能恢复稳定底部安全距离
- 能满足“发送后先把用户消息顶到 header 下方，随后自然回落”的目标体验
