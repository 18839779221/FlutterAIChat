# 聊天时间线滚动策略设计

## 背景

当前 App 的消息列表已经出现多类滑动异常，表面症状包括：

1. `ask_user_question` 卡片出现后，有时卡片自身会承接纵向滑动，导致外层时间线无法连续滚动
2. 部分场景中会出现“手指放在消息卡片上拖动，但整体列表滑不动”的偶发现象
3. `create_artifact` 的 inline 预览使用 `WebView`，其平台视图特性天然更容易引入嵌套手势和高度变化风险

这些问题背后不是单个组件实现失误，而是聊天页尚未正式确立一套统一的滚动 ownership 规则。当前代码同时存在：

- 聊天页外层主时间线 `ChatMessageList`
- `AskUserQuestionCard` 内部纵向 `ListView`
- artifact inline 预览的独立平台视图
- markdown 表格、代码块等局部滚动容器

如果不先定义统一策略，后续每新增一种卡片，都可能再次引入新的嵌套滑动冲突。

## 目标

本次设计目标如下：

1. 明确聊天页只有一个纵向主滚动面，并把该规则落到组件级约束
2. 消除 `ask_user_question` 与主时间线之间的纵向嵌套滑动
3. 明确 `create_artifact` 在聊天时间线中的展示边界，避免其成为第二个纵向滚动视口
4. 为 markdown、代码块、表格、tool 卡片等其他消息内容建立统一滚动规范
5. 建立可回归的测试与验收标准，避免后续再退化回多纵向滚动面

## 非目标

本轮明确不做以下事情：

1. 不重写聊天页整体布局结构
2. 不在本轮实现 artifact 跳变抑制方案，例如占位撑高、历史高度复用或复杂锚点补偿
3. 不为 artifact 增加复杂的折叠、分段展开、渐进展开逻辑
4. 不在聊天时间线里允许新的纵向嵌套滚动例外
5. 不把详情页阅读体验和聊天页滚动策略混为一谈

## 设计原则

### 1. 聊天页只允许一个纵向主滚动面

聊天页中的纵向拖拽、惯性滚动、历史分页、阅读锚点维护，都只能由主时间线统一承担。消息卡片默认只是内容块，不应再拥有自己的纵向 scrollable。

### 2. 默认完整展示，优先保持所见即所得

普通消息卡片、`ask_user_question` 卡片、可内联展示的 artifact，都应尽量在时间线内直接展示内容，而不是默认依赖二级页面阅读。

### 3. 局部滚动优先只允许横向

代码块、markdown 表格、过宽技术内容可以保留局部横向滚动，因为这不会与主时间线争夺纵向手势。

### 4. 超长内容优先做展示边界，而不是再引入内部纵向滚动

如果某类卡片在聊天页内展示不下，应通过“自然截断 + 详情页出口”处理，而不是新增内部纵向滚动区。

### 5. 聊天页和详情页是两个不同的滚动场景

聊天页执行“单纵向主滚动面”规则；详情页属于独立阅读场景，可以拥有自己的滚动容器和更完整的交互能力。

## 总体策略

### 推荐策略：单纵向主时间线

本次采用如下统一策略：

- `ChatMessageList` 是聊天页唯一纵向滚动宿主
- 时间线内所有消息卡片默认不再创建内部纵向 `ScrollView` / `ListView`
- 局部辅助滚动仅限横向场景
- `ask_user_question` 完全并入主时间线
- artifact 在聊天页内只做 inline 展示或进入详情页，不在时间线内承接内部纵向滚动

这套策略的核心收益是把所有纵向手势 ownership 收拢到一个地方，避免“卡片自己滚”和“整页滚”并存时产生的抢手势、失去惯性链路、偶现滑不动等问题。

## 组件级约束

### 1. `ChatMessageList`

`ChatMessageList` 是聊天页唯一纵向滚动宿主，独占以下职责：

1. 纵向拖拽与惯性滚动
2. 历史消息分页加载
3. 最新消息附近的 follow-latest 行为
4. 用户浏览历史时的 manual-browse 行为
5. 长内容卡片高度变化后的阅读锚点维护

消息卡片不允许反向拥有或修改这些职责。任何“滚到底部”“保持当前位置”“加载更多”的状态切换，都必须由主时间线统一处理。

### 2. `AskUserQuestionCard`

`AskUserQuestionCard` 应从“内部可滚动卡片”收敛为“普通内容块”：

1. 移除内部纵向 `ListView`
2. 不再使用 `maxHeight + Expanded + inner scroll` 组合来限制其主内容区域
3. 卡片高度随内容自然增长，由主时间线承担纵向滚动
4. 多题切换、选项点击、`Other` 输入框显隐等交互，只允许改变卡片布局，不允许改变滚动 ownership

这意味着 `ask_user_question` 在聊天页中虽然是强交互卡片，但它仍然只是时间线中的一个普通 block，而不是 block 中再嵌一个纵向页面。

### 3. `create_artifact` / artifact inline 预览

artifact 的目标不是“附件小窗”，而是“大模型回答结果的一种富内容呈现方式”。但在本轮约束下，它仍需遵守聊天页单主滚动规则：

1. 聊天时间线内的 artifact inline 预览不承接内部纵向滚动
2. 能完整展示的内容直接在时间线中展示
3. 展示不下的内容可以保留截断，并提供进入详情页的明确出口
4. 详情页内允许 `WebView` 自身滚动，因为那是独立阅读场景

本轮不为 artifact 增加复杂折叠展开，也不把“减少流式高度跳变”作为本次滚动策略实现的一部分。

### 4. markdown / 表格 / 代码块

这类内容统一归入“允许局部横向滚动，禁止局部纵向滚动”的类别：

1. markdown 表格可以横向滚动
2. 关闭自动换行的代码块可以横向滚动
3. 不因内容过高而再包一层内部纵向 `SingleChildScrollView`

这保证技术内容仍然可读，同时不破坏聊天页纵向手势的唯一性。

### 5. tool workflow / tool result / structured output

这类卡片默认也视为普通内容块：

1. 能完整展示则完整展示
2. 过长时优先通过内容裁剪、结构精简或未来的轻量折叠处理
3. 不默认引入内部纵向滚动容器

后续如果某类 tool 卡片确实必须引入更复杂的内部交互，应被视为显式例外设计，而不是沿用普通卡片滚动模式。

## 长内容、流式更新与阅读锚点

去掉内部纵向滚动后，风险会从“嵌套滑动冲突”转移到“卡片高度变化造成时间线跳动”。因此主时间线需要明确维护两类状态：

### 1. `follow-latest`

当用户停留在最新消息附近时，允许以下变化自然推动时间线保持贴近最新内容：

1. 普通 assistant 文本流式增长
2. `ask_user_question` 因交互显隐带来的高度变化
3. artifact inline 预览因 HTML 重新测高带来的高度变化

### 2. `manual-browse`

当用户已经离开最新消息区域时：

1. 任何卡片高度变化都不能强制把用户拉回底部
2. 卡片只能影响当前位置附近的布局
3. 不允许子卡片自行“补偿滚动”来修改用户当前阅读位置

这套规则的重点不是“某张卡片会不会变高”，而是“无论谁变高，都只能交由主时间线处理视口变化”。

## artifact 边界补充说明

针对 artifact，需要明确三个层次：

### 1. 聊天时间线的职责

聊天时间线负责：

1. 承载 artifact 的 inline 呈现
2. 允许其成为回答本体的一部分
3. 在展示不下时保留清晰详情页入口

聊天时间线不负责：

1. 提供 artifact 的内部纵向滚动体验
2. 提供复杂的长文档阅读交互
3. 在本轮解决所有流式测高引发的跳变问题

### 2. 详情页的职责

详情页负责：

1. 承载完整 artifact 阅读
2. 允许 `WebView` 自身滚动
3. 提供更专注的查看环境

### 3. 后续优化边界

artifact 跳变优化是独立议题，可在统一滚动策略稳定后单独推进。潜在方向包括：

1. 复用历史已测高度
2. 用占位背景或稳定容器减轻回流跳变
3. 对流式更新进行更强节流
4. 在主时间线侧做更细的锚点补偿

但这些都不应与本次“单纵向主滚动面”收敛工作耦合。

## 实现建议

### 任务 1：收敛聊天页主滚动模型

1. 审视 `ChatMessageList` 当前的 scroll listener、分页触发、初始定位和 follow-latest 逻辑
2. 把“谁负责纵向滚动”作为组件边界显式化
3. 禁止消息卡片层创建新的纵向主视口

### 任务 2：移除 `AskUserQuestionCard` 的内部纵向滚动

1. 移除内部 `ListView`
2. 调整布局结构，使其成为自然高度的普通卡片
3. 补充长问题、长选项、`Other` 输入场景的回归测试

### 任务 3：明确 artifact 在聊天页内的展示边界

1. 维持 inline 预览不承接内部纵向滚动
2. 保留截断与详情页入口
3. 不在本轮引入复杂折叠展开逻辑
4. 不把跳变优化与滚动策略改动混做一件事

### 任务 4：统一其他消息内容的滚动规则

1. 保留代码块、表格等横向滚动
2. 清点是否存在其他隐藏的纵向 scrollable
3. 将“禁止局部纵向滚动”落实到通用渲染约束和测试中

## 测试与验收标准

### 1. 主时间线滚动 ownership

1. 聊天页内只有 `ChatMessageList` 承担纵向滚动
2. 用户手指落在普通消息、`ask_user_question`、artifact inline 区域上拖动时，整体时间线都能连续滚动
3. 不再出现“卡片自己吃掉纵向拖拽导致整页滑不动”的场景

### 2. `AskUserQuestion` 回归

1. `AskUserQuestionCard` 不再包含内部纵向 `ListView`
2. 长问题、长选项、显示 `Other` 输入框时，卡片随内容自然增高
3. 多题切换、选项点击、文本输入时，不出现局部纵向滚动抢手势
4. 现有“single scroll surface”语义应有稳定测试覆盖

### 3. artifact 回归

1. 聊天页中的 artifact inline 预览不承接内部纵向滚动
2. 能展示的内容在时间线内直接展示
3. 展示不下时保留进入详情页的可发现入口
4. 详情页中允许 `WebView` 内部滚动

### 4. 辅助内容回归

1. markdown 表格、代码块等仅保留横向辅助滚动
2. 不新增新的内部纵向 scrollable
3. 历史分页、切换会话、流式回复期间，主时间线 follow-latest / manual-browse 语义不被卡片层打破

## 风险与取舍

### 1. 失去局部纵向滚动后，单条卡片可能更高

这是有意取舍。我们用“聊天页滚动 ownership 明确”换取“局部卡片不再自带小滚动容器”。短期内消息块会更高，但整体手势模型会更稳定。

### 2. artifact 的流式跳变仍可能存在

本轮接受这一现实，并把它作为后续独立体验优化议题，而不是和当前滚动策略收敛一起改。

### 3. 详情页滚动与聊天页滚动策略不同

这不是不一致，而是场景不同。聊天页是对话时间线，详情页是专注阅读页，允许不同滚动模型。

## 结论

本次应正式确立如下规则：

1. 聊天页只有一个纵向主滚动面，即 `ChatMessageList`
2. `ask_user_question` 在聊天页内完全并入主时间线，不再拥有内部纵向滚动
3. artifact 在聊天页内只做 inline 展示或跳转详情页，不在时间线中承接内部纵向滚动
4. markdown / 表格 / 代码块等仅保留横向辅助滚动
5. artifact 跳变优化、复杂折叠展开逻辑不纳入本轮实现范围

这套策略优先解决当前已经暴露出的嵌套滑动冲突，并为后续消息卡片演进建立统一边界。
