# 首页顶部 Chrome 动效设计

## 摘要

本设计只面向首页顶部 chrome 区域的动效语言，不继续扩展按钮视觉样式，也不触碰消息列表、输入区、抽屉或工具卡片。

当前顶部按钮已经完成一轮玻璃材质统一，但整体仍偏静态：按钮各自成立，缺少整组收拢、展开、呼吸的共享状态，因此页面在滚动和停驻时没有形成明确的节奏与空间感。用户希望先做“加法”，先看到更灵动、更有状态切换感的上限版本，再从中做减法收敛。

本设计采用“整组一起收拢”的主路径，并吸收少量错峰节奏。目标不是把顶部做成夸张的表演层，而是让顶部从“松散悬浮”进入“聚焦阅读”的过程中，形成可以被感知的空间组织与材质联动。

## 目标

### 体验目标

- 顶部 chrome 在页面停驻、开始滚动、进入阅读状态时，具备明确且连续的状态切换。
- 灵动感主要由节奏感与空间感构成，材质作为承载层配合变化，而不是单独依赖颜色或 blur 强度。
- 按钮之间不再只是独立 hover / press 反馈，而是归属于同一套共享的顶部场域。
- 顶部变化在视觉上明显，但不能压过正文内容，不破坏聊天阅读的主次关系。

### 架构目标

- 继续复用现有真实组件路径，不创建只服务于 demo 的平行组件系统。
- 顶部按钮继续基于现有共享玻璃按钮能力扩展，不回退到单页私有实现。
- 动效设计先在 Flutter Lab 中验证，再反向收敛到真实首页顶部组件。
- 验证流程保持固定：优先热重载 / 浏览器刷新，固定同一 web origin，需要设备体验时再安装 Android debug 包。

## 非目标

- 不在本设计中重新定义顶部按钮的最终色板规范。
- 不处理输入区、消息列表、底部工具栏、抽屉等其他区域的动效细节。
- 不引入 HTML/CSS 独立 demo；需要展示时一律通过 Flutter Lab。
- 不把顶部做成持续高频、强注意力的动画组件。
- 不在本设计中直接规定所有 press / hover / long press 的实现参数，交互微态只在与滚动状态耦合时讨论。

## 现状问题

### 1. 只有局部质感，没有整组状态

顶部按钮虽然已经向输入框的玻璃效果靠拢，但更多是“单个按钮变得更像玻璃”，而不是“顶部整体成为一个会随阅读状态变化的系统”。

### 2. 背景场缺位

目前用户感知到的主要是按钮本体，而不是按钮之间共享的空间关系。结果是按钮像几个并列的控件，而不是悬浮在同一层空气里的 chrome。

### 3. 节奏不成立

如果所有元素同步、等幅、等速地变化，用户能看出变了，但感受不到“聚拢”或“落位”。灵动感需要先后关系，需要环境先变、物体再跟进。

## 设计方向

本次顶部 chrome 的方向定义为：

**从松散悬浮到聚焦收拢的共享玻璃场。**

这句话对应三层含义：

1. 顶部不是固定控件条，而是一个会随滚动进入不同状态的区域。
2. 动效主角不是单个按钮，而是整组 chrome 的空间组织方式。
3. 材质变化服务于“聚拢”和“稳定”，而不是服务于“更花哨”。

## 状态模型

顶部 chrome 定义三个状态：

### 1. Relaxed

页面停在顶部或接近顶部时的默认状态。

特征：

- 按钮间距更松
- 整组视觉重心更分散
- 玻璃更透、更柔，边缘向外轻微化开
- 阴影更长、更轻，呈现漂浮感

### 2. Transition

从顶部开始滚动到进入稳定阅读状态之间的连续过渡区。

特征：

- 整组开始向中轴轻微聚拢
- 共享背景场先发生变化
- 各按钮随后跟进
- 材质从“散雾”走向“亮芯更集中”

### 3. Gathered

进入阅读状态后的稳定顶部。

特征：

- 左右按钮组更收、更稳
- 图标按钮仍保持圆形，但更像嵌在同一层玻璃场上
- 玻璃更白、更亮一点，边缘更贴合本体
- 阴影缩短并更贴近按钮，降低漂浮感，提升聚焦感

## 状态切换触发规则

### 1. 主要触发源

顶部状态由页面垂直滚动位置驱动，不使用离散开关。

### 2. 过渡区间

建议以页面顶部开始的前 `28dp - 44dp` 滚动距离作为主要变化区间。

含义不是“滚动超过某个阈值才突然变化”，而是：

- `0dp` 附近几乎完全处于 Relaxed
- 进入过渡区后快速建立“正在收拢”的感受
- 超过过渡区后逐渐逼近 Gathered

### 3. 方向策略

本轮先做加法，因此允许用户明显感知“从松到紧、从散到收”的切换。

但这个“明显”主要来自：

- 间距变化
- 材质聚焦
- 先后节奏

而不是来自夸张位移、旋转、缩放或高频弹跳。

## 动效结构

顶部 chrome 的变化拆为三层：

### 1. 空间层

负责回答“这些按钮彼此处在什么关系里”。

变化内容：

- 左右两组按钮向中轴轻微靠拢
- 中间 workspace / 标题按钮在收拢态下略微更紧凑
- 整组视觉宽度轻微收缩，形成“阅读中更聚焦”的姿态

建议范围：

- 单侧位移控制在 `4dp - 8dp`
- 不做大幅缩放，只允许极轻微尺寸紧致感

### 2. 材质层

负责回答“这层 chrome 是轻飘的，还是稳定聚焦的”。

变化内容：

- Relaxed 态更透，外缘更柔
- Gathered 态中心亮度略升，白感增强
- 外缘的雾化范围收窄，边缘与主体过渡更自然
- 保留各自阴影体系，不强行统一阴影值，但让阴影在 Gathered 态更短、更贴近

这里的关键不是加深灰色或加粗边框，而是让玻璃从“扩散”变成“聚焦”。

### 3. 节奏层

负责回答“变化是机械同步的，还是有生命感的”。

建议顺序：

1. 共享玻璃背景场先进入收拢
2. 两侧图标按钮跟进
3. 中间 workspace / 标题按钮最后稳定

这样会形成“环境先变，物体再落位”的节奏。

## 区域级规则

### 图标按钮

适用对象：

- 左上菜单
- 右上新建对话
- 右上调试等纯图标按钮

规则：

- 始终保持圆形，不允许在动效过程中退化为圆角矩形
- 允许轻微向中轴移动
- 允许材质亮度与边缘柔化程度变化
- 不做显著尺寸变化，避免图标按钮像在“呼吸放大”

### 中间标题 / Workspace 按钮

规则：

- 在整组节奏里略慢半拍稳定
- 收拢态下文字与玻璃主体的结合感更强
- 不靠放大文本或强烈色差建立状态

它应成为“整组落稳”的最后一个信号，而不是最先抢眼的元素。

### 共享背景场

这是本设计最关键的一层。

虽然用户最终看到的仍然是一个个按钮，但实现上应保留“顶部整组属于同一个微弱背景场”的表达空间。这个背景场不要求成为可见底板，更像是一层弱化的玻璃空气层。

它的职责是：

- 在 Relaxed 态提供松散、向外扩的氛围
- 在 Gathered 态提供向中部聚焦的包裹感
- 帮助按钮之间建立“同属一组”的关系

## 时长与曲线

### 推荐节奏

- 收拢：`220ms - 260ms`
- 放松回弹：`280ms - 340ms`

### 推荐感受

- 收：更果断
- 放：更松、更慢一点

这样顶部会给人“进入工作状态”与“回到松弛停驻状态”的差别，而不是一个完全对称的 UI 过渡。

### 曲线原则

- 使用带一点黏性的缓动
- 可以有非常轻微的弹性感，但不能做玩具感 spring
- 不要让每一层使用完全一致的曲线

背景场、图标按钮、中间按钮之间允许存在小幅曲线差异，但差异必须服务于层级，不服务于表演。

## 参数映射建议

为了让后续实现保持一致，建议顶部 chrome 的所有视觉变化都收敛到一个统一的滚动进度：

`chromeGatherProgress = 0.0 -> 1.0`

其中：

- `0.0` 对应 Relaxed
- `1.0` 对应 Gathered
- Transition 是中间连续区间

后续所有参数都从这个统一进度派生，而不是每个 widget 自己读取滚动值后独立做判断。

### 建议派生参数

- `groupInsetProgress`：控制左右两组向中轴收拢的程度
- `materialFocusProgress`：控制玻璃从散雾到聚焦的程度
- `shadowTightenProgress`：控制阴影从长软到短贴的程度
- `centerSettleProgress`：控制中间按钮比两侧按钮略晚落稳

### 建议节奏关系

- `groupInsetProgress` 与 `materialFocusProgress` 先启动
- `shadowTightenProgress` 随后跟进
- `centerSettleProgress` 最晚达到终态

这意味着真实实现中可以存在一个共享主进度，再给不同子层增加轻微的 lead / lag，而不是维护多套互相独立的 animation controller。

## Flutter 落地约束

### 1. 先在 Flutter Lab 验证

需要先通过现有 lab 页面把顶部 chrome 的三层状态联动跑通，再回写真实首页顶部。

### 2. 复用真实组件路径

动效参数的承载应继续建立在现有共享玻璃按钮能力之上，而不是再做一套 demo-only widget。

### 3. 保持当前视觉资产边界

本轮只改：

- 顶部整组的状态驱动
- 顶部玻璃场与按钮的联动参数

不改：

- 首页整体布局结构
- 其他区域组件
- 额外导航逻辑

## 验证策略

### Lab 验证

在 Flutter Lab 中至少验证以下场景：

- 页面停在顶部时的 Relaxed 态
- 开始滚动后的 Transition 态
- 进入稳定阅读后的 Gathered 态
- 从 Gathered 回到顶部时的放松过程

### 视觉检查重点

- 是否能一眼看出“整组在收拢”，而不是只是单个按钮颜色变了
- 图标按钮是否始终保持圆形
- Gathered 态是否比 Relaxed 态更白、更亮、更聚焦，而不是更灰、更土
- 边缘过渡是否自然，不出现“本体和外缘割裂”的问题
- 中间按钮是否在节奏上略慢半拍稳定，而不是和其他按钮完全同步

### 验证流程约束

- 固定 web 预览 origin，不随意切换 host 或 port
- 优先使用热重载或浏览器刷新进行快循环
- 每次完成调整后先自检，再与用户沟通
- 若需要真实设备手感，再通过既定 Android debug 安装流程复验

## 风险与取舍

### 1. 风险：顶部抢戏

如果位移、亮度差或节奏差做得过大，顶部会从“有状态”变成“抢阅读注意力”。

对应策略：

- 优先放大整组关系变化
- 控制单个按钮的独立动作幅度

### 2. 风险：材质脏灰化

如果收拢态只是简单加灰、加边框、减透明度，玻璃会变成发闷的塑料块。

对应策略：

- 用亮芯聚焦与边缘柔化范围变化来表达稳定
- 避免把“更稳”误做成“更重”

### 3. 风险：动效只有参数，没有叙事

如果只改时长和 easing，但没有“谁先谁后、谁散谁收”的结构，结果仍会像普通状态动画。

对应策略：

- 把共享背景场作为第一变化层
- 把中间按钮作为最后稳定层

## 后续实施优先级

### 第一阶段

在 Flutter Lab 中建立完整的 Relaxed / Transition / Gathered 三态联动，确认节奏框架成立。

### 第二阶段

把验证过的状态驱动与参数映射回真实首页顶部 chrome，保持组件复用路径一致。

### 第三阶段

在用户看到“上限版本”后，再一起决定做哪些减法，包括：

- 是否减弱位移
- 是否压缩节奏差
- 是否降低材质对比

## 结论

本设计不再把顶部视为几颗独立按钮，而是把它定义成一个会随阅读状态聚拢的共享玻璃 chrome。

它的灵动感主要来自：

- 整组空间关系的收拢
- 玻璃材质从散雾到聚焦的变化
- 共享背景场、图标按钮、中间按钮之间的先后节奏

这样我们先拿到一个“更有生命感”的上限版本，再从真实体验出发做减法，而不是一开始就把顶部压回安全但平的状态。
