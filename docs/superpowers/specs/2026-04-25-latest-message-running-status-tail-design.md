# 最新消息底部运行状态尾注设计

## 背景

当前聊天页会把“工具执行中”等状态文案展示在输入框顶部。这个位置虽然靠近输入区，但不符合用户的主要注意力路径：在 agent/tool loop 执行期间，用户更关注最新消息区域，而不是输入框。结果是状态提示存在，但感知效率偏低，持续执行感也不够自然。

与此同时，当前工具卡片已经开始引入更轻的运行态表达，例如小状态点呼吸、淡扫光等。状态文案如果仍停留在输入区，会造成“状态信息在底部输入区，执行主体在消息区”这一视觉割裂。

## 目标

将当前输入框顶部的运行状态文案迁移到“最新消息块底部”，让用户在阅读最新输出时自然感知系统仍在持续执行。

本次设计目标：

- 让运行状态跟随最新消息，而不是跟随输入区
- 强化“这条输出还在继续”的连续感，而不是新增一个独立的状态组件
- 保持状态提示轻量，不抢正文与 tool card 的注意力
- 与现有刀光 / 呼吸动效语言保持一致

## 非目标

本次不处理以下内容：

- 不重做整个输入区结构
- 不改造 tool card 自身的状态枚举与底层生命周期
- 不引入新的全局悬浮状态栏或底部固定状态条
- 不扩展为多条并行状态的完整面板

## 设计方向

采用“最新消息底部内联状态尾注”的方案。

状态提示不是一条独立插入消息流的新卡片，而是附着在当前最新消息块底部的一段轻量尾注。用户读到最新消息末尾时，可以顺势看到“仍在执行”的状态文案和轻微动效，形成输出尚未结束的心理预期。

该方案强调一体感，而不是显式的系统状态栏。

## 交互方案对比

### 方案 A：附着在最新消息块底部的内联尾注

优点：

- 与最新消息形成一个整体，连续感最强
- 最符合“用户关注最新输出”的阅读路径
- 刀光、状态点等动效可以更自然地服务于“仍在继续”的语义

缺点：

- 需要定义“最新消息块”的稳定归属规则
- assistant 文本流与 tool card 切换时需要保证挂载稳定

### 方案 B：贴在最新消息下方的独立状态贴片

优点：

- 实现边界更清晰
- 不容易影响原有消息块组件结构

缺点：

- 视觉上仍然像一条额外组件
- 一体感弱于内联尾注

### 方案 C：消息列表底部全宽状态条

优点：

- 承载能力强，后续可扩展状态信息

缺点：

- 视觉重量过高
- 容易与输入区、消息区形成新的竞争关系
- 不符合本次“轻提示、持续执行感”的目标

结论：选择方案 A。

## 核心体验

当系统处于持续执行状态时，用户在最新消息底部看到一条轻量尾注：

- 左侧是轻微脉冲的小状态点
- 中间是状态文案，例如“正在联网搜索”“正在读取网页”“正在继续生成”
- 整条尾注表面有很淡的刀光扫过

尾注应当看起来像“最新消息还没结束”，而不是“又增加了一个状态卡片”。

当执行完成后，尾注应直接消失，由消息正文、tool result card、workflow card 自己表达完成结果。本次不保留“已完成”尾注残留态。

## 挂载规则

### 基本规则

运行状态尾注始终挂载在“当前最新的可见输出块”底部。

### 优先级规则

1. 如果当前最新输出是 tool workflow / tool result 卡片，则优先挂在该卡片底部
2. 如果当前最新输出是 assistant 的流式文本消息，则挂在该 assistant 消息底部
3. 如果当前还没有可承载的最新输出块，则不展示尾注

### 稳定性要求

- 同一时刻只允许出现一条运行状态尾注
- 当最新输出块发生切换时，尾注要跟随迁移，不能同时残留在旧块上
- 批量工具并发时，尾注仍然只服务于“最新输出块”，不扩展为多条并行摘要

## 文案策略

文案需要轻量、直接、可持续显示，不强调结果，只强调进行中。

推荐形式：

- 正在联网搜索
- 正在读取网页
- 正在继续生成
- 正在执行工具

文案来源建议：

- 优先复用当前已有的状态摘要或 step 状态文案
- 若 tool 有更具体 summary，则优先使用 tool summary 的轻量进行中版本
- 若拿不到更细语义，则退化为通用文案

本次不在尾注中展示长说明、数量统计或“最多 5 条”等策略信息。

## 视觉规范

### 整体风格

尾注必须足够轻，避免形成新的视觉中心。

要求：

- 高度接近一行附注，不可卡片化
- 不使用独立描边
- 不使用明显底色块
- 不额外显示操作按钮

### 状态点

- 放在文案左侧
- 使用现有运行态语义色，但整体饱和度保持克制
- 维持轻微脉冲

### 刀光

- 只作用于尾注区域，不扫整张消息卡
- 透明度显著低于大卡片 running sweep
- 节奏偏慢，强调持续运行而不是强提醒

### 文案样式

- 字号比正文小一级
- 颜色比正文更弱，但仍需可读
- 与消息正文左对齐，保持阅读节奏连续

## 输入区调整

迁移完成后，移除当前输入框顶部的运行状态文案区域。

输入区职责回归为：

- 草稿输入
- 发送 / 停止 / 交互控制
- 必要的输入相关状态

执行状态不再由输入区承担主展示职责。

## 组件边界建议

本次不建议把这个尾注做成消息体系外的全局层。

建议做法：

- 在消息列表或消息块装配层判断当前“最新可见输出块”
- 将一个轻量尾注组件注入到该块底部
- 尾注组件内部复用已有运行态动效能力，而不是重新复制一套动画实现

建议新增一个聚焦组件，例如：

- `LatestMessageRunningStatusTail`

职责：

- 渲染状态点
- 渲染状态文案
- 渲染尾注级别的刀光

不负责：

- 业务状态计算
- 最新消息归属判定
- 工具结果数据映射

## 数据与状态来源

尾注只消费现有运行态语义，不新增一套 UI 专用状态机。

建议继续基于现有结构推导：

- 当前 turn / tool workflow 的运行状态
- 最新 step / latest tool presentation model
- 最新 assistant 流式输出状态

关键原则：

- 使用共享生命周期语义
- UI 层只做“挂载位置”和“轻量样式”的变化
- 不引入和现有 tool card / workflow card 脱节的新状态定义

## 边界场景

### 仅文本流式输出

尾注挂在最新 assistant 文本消息底部。

### tool workflow 正在执行

尾注挂在最新 tool workflow card 或 research card 底部。

### tool 批量并发

即使后台有多个并发任务，尾注仍只附着在当前最新输出块底部，不做多任务列表。

### 执行完成瞬间

尾注消失，避免保留“已完成”提示造成重复表达。

### 没有最新输出块

不展示尾注，避免孤立悬浮。

## 实现建议

### 第一阶段

- 找出输入区顶部状态文案的现有承载点
- 将其移出输入区
- 在消息列表装配层定位最新消息块
- 为最新消息块注入尾注组件

### 第二阶段

- 复用现有运行态状态点呼吸
- 为尾注增加低强度刀光
- 调整字号、间距、透明度，避免喧宾夺主

### 第三阶段

- 校验 assistant 文本流、tool workflow、tool result、research card 等多种场景
- 保证只显示一条尾注，且随最新块稳定迁移

## 验收标准

- 用户在不看输入框的情况下，也能清楚感知系统仍在持续执行
- 运行状态文案出现在最新消息块底部，而不是输入框顶部
- 尾注看起来像消息的一部分，而不是额外插入的一张卡片
- 刀光仅作用于尾注，强度明显低于大卡片 running sweep
- 执行结束后尾注自然消失，不残留完成态重复文案
- assistant 文本流与 tool card 场景都能稳定工作

## 风险与注意事项

- 如果“最新消息块”归属规则不稳定，尾注可能闪动或错误挂载
- 如果尾注视觉重量过高，会打断正文阅读节奏
- 如果直接复用整卡 sweep，而不缩小作用范围，容易显得过度设计
- 如果尾注也展示太多策略信息，会重新变成用户不关心的噪音

## 结论

本次采用“最新消息底部内联状态尾注”方案，把运行状态从输入区迁移到用户真正关注的最新输出区域。它的核心不是增加一个新组件，而是把“仍在执行”的感知嵌入最新消息的阅读终点，并通过轻量文案、脉冲状态点和低强度刀光传达持续执行感。
