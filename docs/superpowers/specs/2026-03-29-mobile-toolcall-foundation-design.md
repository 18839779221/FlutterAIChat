# FlutterAIChat 移动端 ToolCall 基础设计

## 背景

当前应用已经具备三个与 ToolCall 演进强相关的基础：

1. 可配置的 HTTP LLM 接入，支持运行时切换 `API Key`、`Base URL` 和 `Model`。
2. 类型化消息基础设施，`ChatMessage` 已支持 `contentType` 与 `payloadJson`。
3. 初步的工具决策入口，`BaseLLM.decideToolCall()` 与 `ChatService.prepareToolAssistance()` 已预留了“让模型决定是否调用工具”的能力。

但这些能力仍停留在“有接口、没闭环”的阶段。当前客户端还不能：

- 把工具定义作为正式产品能力暴露给模型；
- 让模型基于用户请求稳定地产生受约束的工具调用；
- 在移动端执行工具并把结果回填到对话；
- 对有副作用的工具展示确认卡片；
- 让用户把某个工具加入自动执行白名单，以平衡安全与易用性。

本设计的目标不是做一个功能堆砌的“工具箱”，而是为 FlutterAIChat 建立一套可演进的移动端 ToolCall 基础设施，使其逐步具备“像 Claude Code 一样利用工具扩展能力”的产品方向，同时贴合移动端场景。

## 目标

- 为客户端建立一套正式的 ToolCall 基础架构，而不是零散的工具分支逻辑。
- 第一版同时覆盖“信息处理”和“个人助理”两类高频场景。
- 让工具调用在消息流中可见、可确认、可回看、可重试。
- 提供默认“平衡型”执行策略：
  - 只读低风险工具默认自动执行；
  - 有副作用工具默认先确认；
  - 用户可按工具名加入自动执行白名单。
- 在确认卡片中支持第三种动作：`继续，以后不再确认`，将当前工具加入白名单。
- 为后续多步工作流和更强 agent 能力预留扩展空间，但第一版只实现稳定的单步工具闭环。

## 非目标

- 第一版不实现多步工具计划器，不支持一次输出并执行多个工具步骤。
- 不把所有手机原生能力一次性接入，例如相册 OCR、定位导航、通讯录、电话、短信等留待后续阶段。
- 不直接复刻 OpenAI 原生 tool call 协议到客户端内部；内部协议以 Flutter 渲染和持久化为优先。
- 不在第一版引入会话级临时授权或参数级白名单。
- 不在本阶段解决云同步、跨设备工具权限同步或服务端代理执行。

## 产品策略

### 默认执行模式

第一版默认使用“平衡型”策略：

- 读取类、低风险、无副作用工具默认自动执行；
- 写入类或有外部副作用工具默认要求用户确认；
- 用户可以通过设置页切换整体模式，但第一版以平衡型为默认体验。

### 白名单机制

第一版白名单采用“按工具名”粒度，而不是按风险等级或场景模板。

这样做的原因：

- 最容易理解和调试；
- 设置项对用户更透明；
- 与确认卡片中的“继续，以后不再确认”动作天然对应；
- 后续可平滑扩展到风险等级或会话级授权，而不破坏数据模型。

### 确认卡片动作

所有需要确认的工具调用在 UI 上必须提供三个动作：

- `继续`
- `取消`
- `继续，以后不再确认`

第三个动作的行为是：

1. 当前这次工具调用继续执行；
2. 将对应 `toolName` 加入自动执行白名单；
3. 后续同名工具在默认平衡模式下按自动执行处理；
4. 该白名单可在设置页随时移除。

第一版中，这个动作只作用于“当前工具名”，不作用于：

- 当前参数组合；
- 当前聊天会话；
- 全部工具。

## 第一批工具范围

第一版建议先做 6 个工具，分为自动执行组与确认执行组。

### 自动执行组

#### 1. `search_chat_history`

用途：

- 从当前会话或历史会话中检索相关消息，辅助长对话记忆。

典型场景：

- “我上次提到的 API 地址是什么？”
- “帮我找之前聊过的数据库方案。”

输入建议：

- `query`
- `scope`
- `maxResults`

默认策略：

- 自动执行。

#### 2. `fetch_webpage`

用途：

- 读取网页正文，供模型总结、提取和整理。

典型场景：

- “总结这个链接。”
- “看看这个网页主要在讲什么。”

输入建议：

- `url`
- `extractMode`

默认策略：

- 自动执行。

### 确认执行组

#### 3. `save_note`

用途：

- 将当前结果保存为应用内笔记或知识库条目。

典型场景：

- “把这个总结存下来。”
- “保存成笔记，标题叫 ToolCall 设计。”

默认策略：

- 需要确认。

#### 4. `create_reminder`

用途：

- 创建提醒事项。

典型场景：

- “提醒我明晚 8 点交周报。”
- “明天早上提醒我带电脑。”

默认策略：

- 需要确认。

#### 5. `create_calendar_event`

用途：

- 创建日历事件。

典型场景：

- “下周一下午 3 点加个会议。”
- “帮我把这个安排放进日历。”

默认策略：

- 需要确认。

#### 6. `share_result`

用途：

- 调起系统分享，将当前结果分享给其他 App 或联系人。

典型场景：

- “把这个总结发出去。”
- “分享这段整理结果。”

默认策略：

- 需要确认。

## 推荐路线

第一版推荐采用：

- **内核按单步工具执行实现**
- **交互层吸收部分确认式工作流**
- **协议层为未来多步计划预留扩展点**

也就是：

- 当前每次最多执行一个工具；
- 对有副作用工具采用确认卡片；
- 工具执行结果写回消息流；
- 后续如要支持多步工作流，可在 orchestration 层扩展，而不推翻当前消息模型。

不推荐第一版直接上多步计划器，原因如下：

- 移动端工具权限和副作用比桌面端更复杂；
- 如果单步工具协议和 UI 还不稳定，多步计划只会放大混乱；
- 当前代码已经有单步工具决策入口，更适合先把闭环做稳。

## 架构设计

### 1. Tool Registry

`ToolRegistryService` 负责统一注册可用工具定义。

每个工具至少声明：

- `name`
- `title`
- `description`
- `parametersSchema`
- `requiresConfirmation`
- `riskLevel`
- `supportedPlatforms`

职责边界：

- 只负责“有哪些工具”和“这些工具长什么样”；
- 不负责判断能不能执行；
- 不负责实际执行工具。

### 2. Tool Policy

`ToolPolicyService` 负责根据默认模式、白名单和工具元数据，判断工具的执行策略。

输出建议是三态之一：

- `auto_run`
- `require_confirmation`
- `blocked`

此外，`ToolPolicyService` 还负责：

- 将某个工具加入自动执行白名单；
- 将某个工具从白名单移除；
- 读取和持久化工具策略设置。

### 3. Tool Decision

`ToolDecisionService` 负责让模型从可用工具里选择是否调用某个工具，并输出严格 JSON 决策。

第一版建议继续复用已有的 `BaseLLM.decideToolCall()`，但把以下职责从 LLM 调用边界外提取出来：

- 可用工具列表组装；
- JSON 解析与校验；
- 非法工具名拒绝；
- 非法参数结构拒绝。

### 4. Tool Execution

`ToolExecutionService` 负责真正执行 Flutter 侧动作。

第一版允许先用受控的 switch/dispatcher 实现，不要求一开始就做插件化架构。

执行结果统一返回强类型结果对象，而不是裸文本。

### 5. Tool Orchestration

`ToolOrchestratorService` 负责串起整条链路：

1. 收到用户消息；
2. 询问模型是否需要工具；
3. 根据策略决定自动执行、确认或阻止；
4. 插入工具调用或确认消息；
5. 执行工具；
6. 插入工具结果消息；
7. 再决定是否让模型基于结果生成最终答复。

这是未来演进为多步 agent 的关键锚点。

### 6. Tool Rendering

消息系统中的工具消息必须作为一等类型存在，而不是只把工具执行结果当成普通文本回填。

渲染层应至少区分：

- 内容卡片
- 确认卡片
- 执行中卡片
- 工具结果卡片

## 内部协议设计

### 为什么不直接复用 OpenAI 原生协议

客户端内部协议不仅要支持模型解析，还要支持：

- 持久化；
- UI 状态展示；
- 用户确认；
- 重试和回放；
- 白名单策略沉淀。

因此，内部协议应优先服务 Flutter 消息流，而不是原样复制上游 API 格式。

### Tool Invocation

用于描述“模型决定调用某个工具”。

建议字段：

- `toolName`
- `arguments`
- `status`
- `summary`
- `requiresConfirmation`
- `decisionReason`

状态建议：

- `proposed`
- `awaiting_confirmation`
- `running`
- `cancelled`

### Tool Result

用于描述“某个工具执行后的结果”。

建议字段：

- `toolName`
- `success`
- `summary`
- `data`
- `errorMessage`
- `durationMs`

### Message Content Type

当前消息类型应从现有三分法扩展为至少：

- `plainText`
- `structuredCard`
- `toolInvocation`
- `toolResult`
- `actionConfirmation`

其中：

- `actionConfirmation` 用于承载确认卡片；
- `toolInvocation` 用于表示正在执行或计划中的调用；
- `toolResult` 用于表示工具执行结果；
- `structuredCard` 仍保留给内容整理类卡片。

## UI 与交互设计

### 第一原则

用户必须一眼看懂三件事：

1. AI 准备做什么；
2. 现在做到哪一步；
3. 最终做成了没有。

工具 UI 不应呈现为日志面板，而应是可读、可控、可回看的消息卡片流。

### 1. 确认卡片

适用于：

- 有副作用工具；
- 未加入白名单的确认型工具。

展示内容：

- 标题：例如 `准备创建提醒`
- 参数摘要：面向用户的字段展示，而不是原始 JSON
- 风险说明：例如“此操作会创建系统提醒”
- 动作按钮：
  - `继续`
  - `取消`
  - `继续，以后不再确认`

第三个动作必须触发白名单写入。

### 2. 执行中卡片

适用于：

- 工具已开始执行，但尚未完成。

展示内容：

- 标题：例如 `正在读取网页`
- 简短描述
- 轻量 loading 状态
- 可选取消按钮

### 3. 结果卡片

适用于：

- 工具成功或失败后。

成功卡片展示：

- 标题：例如 `已创建提醒`
- 摘要：例如时间、标题、目标对象
- 次要按钮：可选 `查看`、`重试`、`继续处理`

失败卡片展示：

- 标题：例如 `创建提醒失败`
- 面向用户的错误摘要
- 重试入口

### 4. 最终答复

工具执行完成后，仍建议由助手生成一条自然语言答复，用来说明：

- 做了什么；
- 结果如何；
- 如有必要，提醒用户下一步。

这样用户看到的是“助手完成任务”的产品体验，而不是“系统执行了一个函数”。

### 5. 详情展开区

每张工具卡片建议保留可折叠的“详情”区域，供高级用户查看：

- 工具名
- 参数摘要
- 执行耗时
- 原始错误摘要

默认折叠，避免把主界面做成日志面板。

## 数据流

第一版标准链路如下：

1. 用户发送消息；
2. `ChatController` 正常写入用户消息；
3. `ChatService`/`ToolOrchestratorService` 判断是否需要工具；
4. 如果不需要工具，走原有聊天链路；
5. 如果需要工具：
   - 查询工具元数据；
   - 查询策略服务；
   - 生成确认卡片或工具调用消息；
6. 自动执行或用户确认后，执行工具；
7. 写回工具结果消息；
8. 如有需要，让模型基于工具结果生成最终自然语言回复；
9. 聊天列表按 `contentType` 渲染工具消息与结果。

## 设置设计

第一版设置页建议新增一个“工具权限管理”区域。

### 建议内容

- 默认执行模式
  - `保守`
  - `平衡`
  - `激进`
- 自动执行白名单
  - 展示已加入白名单的工具名称
  - 支持手动移除

### 白名单来源

白名单有两种进入方式：

1. 设置页手动添加或管理；
2. 用户在确认卡片中点击 `继续，以后不再确认`。

## 与现有代码的集成方式

### LLM 层

保留 `BaseLLM.decideToolCall()` 作为模型决策入口，但将解析和校验职责移出 LLM 具体实现。

### 服务层

`ChatService` 不应承载全部工具逻辑。推荐做法是：

- `ChatService` 继续作为聊天业务入口；
- 新增 `ToolOrchestratorService` 承担工具链编排；
- `ChatService.prepareToolAssistance()` 后续可逐步迁移或委托给 orchestrator。

### Provider / Controller 层

`chat_providers.dart` 中的发送消息流程需要扩展为：

- 先落用户消息；
- 再判断工具；
- 再插入工具消息；
- 再执行工具并写回结果；
- 最后补最终答复。

不建议把所有逻辑直接堆进现有 `sendMessage()`。

### Widget 层

建议新增：

- `ToolConfirmationCardWidget`
- `ToolInvocationCardWidget`
- `ToolResultCardWidget`

并在 `chat_message_list.dart` 中按 `contentType` 分发渲染。

## 测试策略

第一版测试重点应放在“协议、策略、执行边界”上。

### 单元测试

- 工具决策 JSON 解析与非法输入拒绝；
- `ToolPolicyService` 在不同模式、白名单下的决策结果；
- `ToolExecutionService` 对每个工具的成功/失败返回；
- 白名单写入与移除；
- `actionConfirmation` 第三个动作会将工具名加入白名单。

### Widget 测试

- 确认卡片展示三种操作按钮；
- 点击 `继续，以后不再确认` 会走白名单路径；
- 工具结果卡片成功与失败分支均能正确渲染。

### 手动验证

- 自动执行组工具可直接完成执行并回填结果；
- 确认执行组工具先展示确认卡片；
- 点击 `继续，以后不再确认` 后，同名工具后续不再弹确认；
- 设置页中可移除对应白名单条目；
- 工具失败不会破坏普通聊天链路。

## 实施顺序

推荐按以下顺序实施：

1. 扩展消息类型与工具相关模型；
2. 落工具策略与白名单存储；
3. 落只读工具：
   - `search_chat_history`
   - `fetch_webpage`
4. 落确认卡片与三种确认动作；
5. 落副作用工具：
   - `save_note`
   - `create_reminder`
   - `create_calendar_event`
   - `share_result`
6. 最后补设置页中的工具权限管理。

这个顺序能够先把最关键的工具协议、策略和 UI 骨架做稳，再逐步扩充副作用能力。

## 风险与约束

### 1. 工具协议失控

如果模型可以随意输出任意工具名或参数结构，客户端很快会变得脆弱。

约束：

- 工具名必须白名单校验；
- 参数结构必须严格 JSON 校验；
- 非法决策必须拒绝执行。

### 2. 自动执行过度

移动端副作用工具过多自动执行会损害信任感。

约束：

- 第一版只允许低风险读取类工具默认自动执行；
- 有副作用工具默认确认；
- 用户必须能随时撤销白名单。

### 3. 结果展示技术化

如果 UI 暴露过多 JSON 和内部术语，用户会觉得自己在看调试面板。

约束：

- 默认展示自然语言摘要；
- 原始参数和错误放入折叠详情；
- 工具状态统一转化为用户可读文案。

## 验收标准

- 用户发送消息后，系统可以稳定判断是否需要调用第一批 6 个工具之一。
- `search_chat_history` 和 `fetch_webpage` 在默认平衡模式下可自动执行并回填结果。
- `save_note`、`create_reminder`、`create_calendar_event`、`share_result` 会先展示确认卡片。
- 确认卡片必须包含：
  - `继续`
  - `取消`
  - `继续，以后不再确认`
- 点击 `继续，以后不再确认` 会把当前 `toolName` 写入白名单，并在后续同名调用时跳过确认。
- 设置页可以查看并移除自动执行白名单条目。
- 工具消息、工具结果消息与最终答复能在聊天列表中稳定渲染。
- 工具失败不会破坏普通聊天和消息列表渲染。
