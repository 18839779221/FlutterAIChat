# 长期记忆形成层设计

## 摘要

本设计覆盖长期记忆系统的第三阶段：**形成层**。

上一阶段已经把长期记忆接入运行时上下文；本阶段补齐“把对话中值得保留的信息写成记忆文件”的闭环。这里的形成不是全局扫描，也不是关键词规则，而是基于**最近可见消息**的后台抽取：

- 在一次完整 turn 结束后触发。
- 只处理当前模型可见的最近消息片段。
- 用户明确说记住 / 忘掉时优先立即处理。
- 抽取结果通过现有通用文件工具写入 `/memories`。
- 记忆形成后的正文仍由后续使用层按需召回。

本阶段只定义形成策略，不新增新的记忆检索范式，也不引入向量库、定时轮询或全量历史回放。

## 背景

调研 Claude-Code 的长期记忆实现后，可以确认形成层有几个关键特征：

- 触发点不是时间，而是 **turn 结束**。
- 抽取对象不是全量会话原文，而是 **这次 query loop 的可见消息片段**，即当前模型实际看得到的那段上下文。
- 默认每个 eligible turn 都可触发一次抽取，但节流参数可调，默认值为 `1`。
- 抽取器只使用最近消息，不去扫代码、不查 git、不做现状验证。
- 如果本轮主路径已经写了记忆，后台抽取会跳过，避免重复写入。
- 抽取只保存未来会再用得上的信息，且优先更新已有记忆而不是堆积重复条目。

本项目已有的长期记忆使用层已经说明：

- 长期记忆是 runtime user context 的一部分。
- 记忆内容是线索，不是当前事实。
- 记忆相关实现不能污染 session summary、timeline 或 workspace 归属。

因此形成层必须和使用层保持同一套记忆语义，但输入来源和触发机制更严格。

## 设计目标

### 产品目标

- 用户明确说“记住 / 忘掉”时，系统能优先保存或删除对应记忆。
- 当对话中出现值得长期保留的稳定信息时，系统能在 turn 结束后自动形成记忆。
- 抽取出来的记忆应当尽量短、稳、可复用，避免把临时状态写成长期事实。
- 形成层不要为了“多记一点”而牺牲主对话体验。

### 架构目标

- 形成层只看最近消息，不扫代码、不查 git。
- 形成层不新增专用 memory tool，继续通过现有通用文件工具维护 `/memories`。
- 形成层只处理 memory 文件，不改变 workspace、session summary 或 transcript 所有权边界。
- 形成层应尽量和使用层共享同一套记忆分类与 frontmatter 约束。
- 形成层可独立测试，不依赖真实生产环境状态。

## 非目标

本阶段不包含：

- 向量检索或 embedding search。
- 全量会话回放式抽取。
- 记忆管理 UI。
- 记忆质量评分面板。
- 自动修复损坏 frontmatter。
- 对旧记忆做复杂迁移。

## 核心策略

### 1. 触发点

形成层在**每次完整 turn 结束后**触发，而不是按时间轮询。

这里的“turn 结束”指模型完成本轮输出，且该轮不再继续追加新的 tool call 执行链。抽取器应当挂在 turn 结束的后台钩子上运行，避免打断主对话。

如果本轮用户或主路径已经直接写入了记忆文件，则后台抽取应跳过这一轮，避免重复保存同一批信息。

### 2. 输入窗口

抽取器使用的是**当前模型可见的最近消息片段**，不是整个会话的原始 transcript，也不是只有当前用户单条消息。

更准确地说：

- 输入窗口应当对应当前 query loop 中可见的 message list。
- 该窗口从上次抽取游标之后开始。
- 该窗口经过正常上下文裁剪后，仍应保持“最近消息”的语义。

这意味着形成层应该基于“最近消息 + 该轮对话语义”来决定是否写入记忆，而不是基于固定长度的聊天片段标题党。

### 3. 节流

默认策略是：每个 eligible turn 都可以抽取一次，`N = 1`。

为了避免高频写入导致：

1. 记忆文件快速膨胀。
2. 抽取任务带来过多额外 token 消耗。

形成层需要保留 turn 级节流能力：

- 允许按 eligible turn 数跳过抽取。
- 默认值保持最小化，即 `1`。
- 后续如需要更保守的频率，可通过配置把 `N` 调大，但不把时间作为主节流依据。

### 4. 显式请求优先

如果用户明确要求：

- 记住某件事。
- 忘掉某件事。
- 更新一条旧记忆。

则应优先处理显式请求，而不是等后台抽取自然命中。

显式请求的处理应优先于普通 turn 结束抽取，因为它代表用户已经明确给出长期记忆意图。

### 5. 抽取范围

形成层只允许使用最近消息中已经出现的信息，不允许为了“补全”去做额外调查。

禁止：

- grep 代码库来验证一条记忆是否成立。
- git blame / git log 来补事实。
- 读取当前文件状态来替代对话内容。

允许：

- 读取现有 memory 文件，判断是否应更新已有条目。
- 使用当前最近消息判断是否值得形成新记忆。

### 6. 记忆分类

形成层沿用四类记忆：

- `user`
- `feedback`
- `project`
- `reference`

分类语义与存储层 / 使用层保持一致：

- `user`：用户角色、偏好、经验、工作方式。
- `feedback`：用户纠正、确认、偏好、成功/失败反馈。
- `project`：当前项目目标、约束、事故、截止日期、协作背景。
- `reference`：外部系统入口与用途。

### 7. 去重与更新

形成层要优先更新已有记忆，而不是不断创建新文件。

基本规则：

- 先查现有记忆文件。
- 如果同一主题已有可更新条目，优先编辑。
- 只有在确实没有合适条目时才新建。
- 对过时、错误、重复的信息，应更新或删除，而不是继续累积。

### 8. 体积控制

形成层需要避免把记忆系统做成无限膨胀的日志。

因此应保留这些硬约束：

- 单次抽取只处理最近消息。
- 单次抽取最多保存少量高置信记忆。
- 生成的索引应保持简短。
- 记忆正文应短小、结构化、可复用。

### 9. 失败退化

抽取失败时，不能阻断主对话。

允许的退化方式：

- 跳过本轮记忆形成。
- 保留用户可见聊天继续进行。
- 只记录 debug 级错误，不向用户输出抽取异常。

## 与使用层的关系

形成层只负责“写成文件”。

使用层负责：

- 读取 `MEMORY.md`。
- 选择相关 topic files。
- 将记忆作为 runtime context 注入。

两者边界应保持清晰：

- 形成层不负责召回排序。
- 使用层不负责决定何时写入。

## 错误处理

### 用户明确说不要使用记忆

如果本轮用户明确要求 ignore memory / not use memory，则形成层不应借机写入新记忆，也不应把该轮当作常规抽取候选。

### 记忆文件冲突

如果抽取出的内容和已有记忆冲突，应优先更新旧条目，而不是保留矛盾并新增一条。

### 读写异常

文件读写失败应降级为“不形成记忆”，不能影响聊天、工具执行或 turn 完成。

## 测试策略

### 抽取触发

覆盖：

- turn 结束时触发抽取。
- 当本轮已直接写 memory 时跳过后台抽取。
- 节流参数 `N` 生效。

### 输入窗口

覆盖：

- 只读取最近可见消息，不扫全量会话。
- 从上次抽取游标之后继续处理。
- 显式记忆请求优先于普通抽取。

### 写入策略

覆盖：

- 优先更新已有记忆。
- 仅在必要时新建 topic file。
- 过大内容会被截断或拒绝进入长期记忆。

### 失败退化

覆盖：

- reader / writer 异常不阻断主对话。
- 抽取失败不会污染 session summary 或 runtime context。

## 验收标准

- 形成层以 turn 结束为主触发点，而不是按时间轮询。
- 抽取对象是当前可见的最近消息窗口，而不是全量会话原文。
- 默认节流为 `N = 1`，并保留调大节流的能力。
- 用户显式记住 / 忘掉优先于后台抽取。
- 形成层不会通过额外调查来补事实。
- 形成失败不会阻断聊天。
- 所有相关测试通过。
